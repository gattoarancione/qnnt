================================================================================
 qnnt examples -- running the C, C++ and Python demo nodes
================================================================================

There are five demo node roles. Each language has ONE program that can play any of
them, chosen by its first argument, so the same five roles exist three times over:

    role 0   publish test/topic-a at 100 Hz and test/topic-b at 20 Hz
    role 1   publish test/topic-c at 1 kHz, and subscribe to test/topic-a
    role 2   subscribe to test/topic-b and test/topic-c (no publishing)
    role 3   TLD load generator on test/bench   [period_us] [payload_bytes]
    role 4   TLD benchmark subscriber on test/bench   [report_ms]

Topics and rates are identical across the languages, so any mix interoperates: a C
role 0 feeding a Python role 2 is the same system as five Zig nodes.

Each node runs in the foreground and prints continuously, so give each one its own
terminal. Stop any of them with Ctrl-C.


--------------------------------------------------------------------------------
 1. Build first (once)
--------------------------------------------------------------------------------

From the repository root:

    zig build

That produces everything the examples need:

    zig-out/bin/node-c          the C program
    zig-out/bin/node-cpp        the C++ program
    zig-out/lib/libqnnt_c.*     the shared library the Python package loads
    zig-out/include/            qnnt.h, qnnt_tld.h, qnnt_tld.hpp

For the benchmark roles (3 and 4) build optimised instead, or the numbers measure
a debug build:

    zig build -Doptimize=ReleaseFast


--------------------------------------------------------------------------------
 2. Run the demos
--------------------------------------------------------------------------------

All commands are run from the repository root.

C
    ./zig-out/bin/node-c 0
    ./zig-out/bin/node-c 3 1000 64

C++
    ./zig-out/bin/node-cpp 1
    ./zig-out/bin/node-cpp 4 1000

Python
    python3 python/nodes.py 2
    python3 python/nodes.py 3 1000 64

The Python package finds the freshly built shared library by itself when run from a
checkout -- no PYTHONPATH, no LD_LIBRARY_PATH, nothing to export. It needs no
dependencies beyond the standard library.

All five roles also exist as standalone Zig binaries (section 9), and every one of
them -- C, C++, Python and Zig alike -- honours the same QNNT_* variables described
in sections 6 and 7. They agree because there is one implementation, inside the
library: each program calls for it in a single line rather than parsing the
environment itself.

An unset or empty variable is simply absent -- 'export QNNT_CLUSTER_KEY' with no
value means unset, not an empty key. A value that cannot be used is reported rather
than ignored:

    ignoring QNNT_REGISTRY_PORT=notanumber: not accepted

Reading it is an explicit call, not something starting a node does implicitly, so a
program that embeds qnnt is never reconfigured by process-wide state behind its
back. In Python the environment is read first and keyword arguments override it:

    qnnt.Node(registry_port=9999)     # wins over QNNT_REGISTRY_PORT

Via the build system instead, which rebuilds first if needed:

    zig build run-c   -- 0
    zig build run-cpp -- 3 1000 64


--------------------------------------------------------------------------------
 3. A three-language system (three terminals)
--------------------------------------------------------------------------------

Pick a registry port so this run cannot collide with anything else you have
going, and use the SAME port in every terminal -- that is what makes the nodes
find each other.

  Terminal 1 -- C publisher:

    export QNNT_REGISTRY_PORT=22400
    ./zig-out/bin/node-c 0

  Terminal 2 -- C++ publisher and subscriber:

    export QNNT_REGISTRY_PORT=22400
    ./zig-out/bin/node-cpp 1

  Terminal 3 -- Python subscriber:

    export QNNT_REGISTRY_PORT=22400
    python3 python/nodes.py 2

Terminal 2 prints test/topic-a arriving from the C node:

    [1787918548717.511] (+7229us) node-cpp 1 received on test/topic-a: ciao!

Terminal 3 prints both topic-b (from C, 20 Hz) and topic-c (from C++, 1 kHz),
each with its own counter:

    [1787918548686.916] (+49274us) node-py 2 feed b #140 on test/topic-b: !oaic
    [1787918470730.900] (+1000us) node-py 2 feed c #6981 on test/topic-c: hola!

Start the terminals in any order. A subscriber whose topic does not exist yet
retries, so nothing has to be brought up first.


--------------------------------------------------------------------------------
 4. The TLD benchmark (two or three terminals)
--------------------------------------------------------------------------------

One publisher, any number of subscribers, in any languages.

  Terminal 1 -- generate load (1 kHz, 64-byte payloads):

    export QNNT_REGISTRY_PORT=22402
    ./zig-out/bin/node-c 3 1000 64

  Terminal 2 -- measure it:

    export QNNT_REGISTRY_PORT=22402
    ./zig-out/bin/node-cpp 4 1000

  Terminal 3 -- measure it from Python too:

    export QNNT_REGISTRY_PORT=22402
    python3 python/nodes.py 4 1000

Typical output, same stream seen from both:

    node-c 3 sent 1000 frames/s (87.9 KB/s), 10044 total
    node-cpp 4 1000 frames/s | wire 87.9 KB/s | lat us min 28 mean 63 p50 64
              p99 96 max 355 | gaps 0 badpay 0 err 0 | 9004 total
    node-py 4 1000 frames/s | wire 87.9 KB/s | lat us min 81 mean 190 p50 210
              p99 268 max 673 | gaps 0 badpay 0 err 0 | 7003 total

Reading it:

  gaps      missing sequence numbers. Should be 0; anything else means frames
            were mis-parsed, since TCP does not lose bytes.
  badpay    payload bytes that did not match the generator's 0..255 pattern.
            Should be 0. The pattern deliberately contains 0x0A and 0xFF, so a
            framing mistake shows up here.
  lat       encode -> publish -> loopback -> read -> decode, end to end. It is
            not decode cost; the decoder itself is tens of nanoseconds.

The latency difference between the two subscribers is the cost of the language
boundary, not of the protocol: Python pays for the ctypes crossing and for
building an object per message.

Other rates to try:

    ./zig-out/bin/node-c 3 10000 64      100 Hz
    ./zig-out/bin/node-c 3 50 64         20 kHz
    ./zig-out/bin/node-c 3 0 64          unpaced -- as fast as the machine goes,
                                         which will busy one core
    ./zig-out/bin/node-c 3 2000 65536    500 Hz of 64 KiB payloads (~32 MB/s)

A pure-Python generator (python3 python/nodes.py 3 1000 64) reaches roughly
950-1000 frames/s rather than a flat 1000: the interpreter, not the transport. It
reports what it actually achieved.


--------------------------------------------------------------------------------
 5. Inspecting a running system
--------------------------------------------------------------------------------

The registry speaks a plain line protocol, so any running system can be examined
with netcat. Use the port your nodes are on:

    nc 127.0.0.1 22400

Then type:

    help                    the command list
    list                    every topic: publisher, subscriber count, age,
                            origin, state
    subs test/topic-a       who is subscribed to a topic: address, connected,
                            messages
    peers                   other REGISTRIES federated with this one -- not the
                            subscribers of a topic, which is 'subs'
    status                  uptime, topic count, node id, addressing, timings
    quit

Three commands answer three different questions, and the middle two get mixed up:

    list          which topics exist, and how many subscribers each has (a count)
    subs <topic>  WHO those subscribers are, by address
    peers         which other registries this one federates with

For example:

    # topic         publisher              subs  refreshed  age   origin  state
      test/topic-a  tcp://127.0.0.1:60373  1     1.5s       6.0s  local   live
      test/topic-c  tcp://127.0.0.1:60377  0     0.5s       5.0s  82ff671c  live
    # 2 topic(s)
    # end

    # subscribers of test/topic-a, reported 0.4s ago
    # subscriber       connected  msgs
      127.0.0.1:58146  1.7s       179
    # 1 subscriber(s)
    # end

Reading the columns:

  origin    "local" if a node on this host publishes it, otherwise the first 8
            hex digits of the node that does. Anything not "local" arrived by
            federation (section 7).
  state     live, stale (the publisher has stopped refreshing), or CONFLICT --
            two hosts publishing the same topic name. On a conflict each host
            keeps its own publisher and flags the clash rather than silently
            hiding one of them.

Lines beginning with '#' are commentary and are ignored by the nodes themselves,
so anything shown to a human can be added without breaking a parser. Every
non-empty reply ends with '# end', which is how a client knows a multi-line reply
is complete instead of having to guess with a timeout.

THAT TERMINATOR IS NOT COSMETIC, and it is the sort of thing a later tidy-up
removes for looking redundant. The protocol had no terminator at first, so a
client reading a multi-line reply had no way to know it had all of it: the
registry keeps the connection open after answering, so waiting for a close meant
waiting out the socket timeout on every single command. Measured before the fix,
at 81.6 ms per command against 0.47 ms once the reply says where it ends -- about
170 times slower, on replies that take under a millisecond to produce.

It also bites instruments rather than programs, which is what makes it expensive
to find. examples/registry/failover.py read until its socket timed out and so
added roughly two seconds to every measurement it reported, making a failover
that took 0.2 s look like one that took 2 s.


--------------------------------------------------------------------------------
 6. The registry port
--------------------------------------------------------------------------------

Nodes find each other through a registry on a well-known port, default 2222. The
first node to start plays the registry; the rest stand by and take over if it
exits.

Nodes on DIFFERENT ports are completely independent. Use that to keep a demo run
away from anything else, and to run several unrelated systems on one machine:

    QNNT_REGISTRY_PORT=22400 ./zig-out/bin/node-c 0

QNNT_REGISTRY_PORT is read by the example programs, not by the library -- the
library takes a port and leaves it to the caller to decide where it came from:

    C / C++    qnnt_set_registry_port(port)   before qnnt_init()
    Python     qnnt.Node(registry_port=port)
    Zig        qnnt.setRegistryPort(port)      before qnnt.run()

If a node prints

    registry standing by (port 22400: error.AddressInUse)

then another node already holds that port, which is normal and expected: exactly
one node is the registry at a time. If you did not intend to share, use a
different port.


--------------------------------------------------------------------------------
 7. Spanning more than one host (federation)
--------------------------------------------------------------------------------

Everything above runs on one machine: the registry is host-local, and nodes find
each other through it. Federation joins the registries of several hosts, so a
subscriber on one host resolves a topic published on another and connects to it
without knowing it is remote.

The cluster key is the switch. Set one and federation starts; leave it unset and
it does not:

    QNNT_CLUSTER_KEY=some-secret   shared by every node in the cluster -- REQUIRED
    QNNT_PEERS=10.0.0.8,nodeb.local  address or hostname, optional :port, comma-separated
    QNNT_RT_PRIORITY=40             SCHED_FIFO priority for worker threads (Linux)
    QNNT_LOCK_MEMORY=1              pin pages with mlockall (Linux)
    QNNT_FEDERATION_PORT=2223      optional; 2223 by default, and 0 disables

The key is not optional because an unauthenticated directory reachable from a
network lets anyone redirect a topic's subscribers, which is worse than not
federating at all.

A node always reports which way it went, on its first lines of output:

    federation enabled: port 2223, 1 peer(s) to dial, binding 0.0.0.0
    federation listening on 0.0.0.0:2223

or, with no key:

    federation disabled: no cluster key. Set one to enable it -- an
    unauthenticated directory on a network lets anyone redirect a topic's
    subscribers.

On real hosts that is the whole configuration: a key everywhere, and each node's
QNNT_PEERS naming the others. The port only needs setting when several nodes share
one machine, since they cannot all bind 2223 -- and a node that loses that race
says so rather than failing quietly.

Peers may be given as addresses or as hostnames. Names go through the system resolver, so
/etc/hosts, resolv.conf, search domains and mDNS names all work:

    QNNT_PEERS=nodeb.local,10.0.0.9:2223,[fe80::1]:2223,fe80::2

The port is optional and defaults to QNNT_FEDERATION_PORT. An IPv6 address needs brackets
only when a port follows it -- without them there is no telling where the address stops.

A name is re-resolved on every connection attempt rather than once at startup, so a peer
that changes address is followed, and a name that does not resolve until the network comes
up needs no restart. The address a name resolved to is reported next to it:

    federation: synced with nodeb.local:2223 (10.0.0.9)

A name that does not exist is reported as UnknownHost, and one that may work later -- no
DNS server reachable yet -- as TemporaryResolveFailure, so a peer that never connects says
why. QNNT_ADVERTISE_ADDR and QNNT_BIND_ADDR accept names too, but resolve once at startup
and are stored as the resulting address: what a publisher advertises has to be something
every subscriber can parse, including ones that cannot resolve the name.


  Terminal 1 -- host A, publishing:

    export QNNT_CLUSTER_KEY=some-secret
    QNNT_REGISTRY_PORT=24101 QNNT_FEDERATION_PORT=24201 ./zig-out/bin/node-c 0

  Terminal 2 -- host B, subscribing, told where A is:

    export QNNT_CLUSTER_KEY=some-secret
    QNNT_REGISTRY_PORT=24102 QNNT_FEDERATION_PORT=24202 \
      QNNT_PEERS=127.0.0.1:24201 python3 -u python/nodes.py 2

(The two ports per node let both "hosts" run on one machine for a look at it;
across real machines every node can keep the defaults and differ only in
QNNT_PEERS.)

B's registry then holds A's topics, marked with A's node id, and B's subscriber
receives across the link:

    # topic         publisher              subs  refreshed  age   origin    state
      test/topic-a  tcp://127.0.0.1:55451  0     2.5s       7.5s  d5ee8c33  live
      test/topic-b  tcp://127.0.0.1:55453  1     2.5s       7.5s  d5ee8c33  live

    nc 127.0.0.1 24102   ->   peers
    # peer                state      last sync  learned  attempts
      127.0.0.1:24201     connected  2.5s             4         1
    # plus 0 entr(ies) applied from peers that dialed us

Notes worth having before deploying this:

  Peer lists need not be symmetric. A node that dials nobody still federates
  with anyone who dials it, and an entry learned from one peer is passed on to
  the others, so a chain converges. A full mesh converges in one hop and is the
  safer choice across gateways.

  Nodes do not need to know their own address. An entry carries a port and,
  optionally, a host; when the host is absent the peer substitutes the address
  it reached the sender on. So a node can sit behind a gateway that chooses its
  public address and still be reachable. Set QNNT_ADVERTISE_ADDR only to
  override that -- to pin a specific interface, say.

  Turning federation on therefore also opens the sockets. With no federation
  port, the federation listener does not exist and publishers bind loopback, so
  nothing is reachable from another machine. Set a federation port and both the
  federation listener and the publisher sockets bind 0.0.0.0, because peers have
  to be able to reach them and no configured address is needed to allow that.
  The registry port itself is never exposed: it stays on loopback in every case,
  which is what keeps 'unpub' and the inspection commands local.

  Changes propagate in milliseconds where a peer connection exists to push over,
  and otherwise within one 5-second anti-entropy round. A node that only listens
  cannot push, so a mutual mesh is what makes propagation immediate.

  Entries whose origin goes quiet age out on their own: stale after 6s, no longer
  handed out after 30s, forgotten after 5 minutes. There is no distributed delete
  to go wrong -- 'unpub' simply stops refreshing.

  Across the internet, run qnnt over a VPN or tunnel and treat that as a LAN. The
  cluster key protects the directory's integrity, but the data plane
  (publisher -> subscriber) has no authentication at all: anyone who can reach an
  advertised publisher port can read that topic. Port-translating NAT without
  forwarding cannot work either way, since inbound connections are impossible.

  MAKING THE DATA PLANE FORWARDABLE: QNNT_PUBLISHER_PORTS

  Federation crosses a firewall easily because it needs one well-known port per
  host. The data plane does not, and the reason is that a publisher binds port 0
  and takes whatever the OS gives it -- nobody can forward a port they cannot
  predict. So the directory reaches the far side and the frames do not.

    QNNT_PUBLISHER_PORTS=2300-2399

  Publishers then take their listening ports from that range, and one rule covers
  every topic on the host. Unset -- the default -- is port 0 and today's
  behaviour exactly: no extra round trip, and no dependency on a registry
  existing before a publisher can bind.

  THE REGISTRY ARBITRATES. Several processes on one host share the range and only
  the registry sees them all, so a publisher asks it (`port <topic>`) rather than
  picking for itself. Two publishers choosing "the first free port" would race;
  choosing by hash would collide. The answer is a port, 0 for "no range here,
  take what you like", or a refusal when the range is full.

  THE ANSWER IS STICKY, and that matters more than it looks. A federated entry is
  served for up to 30 seconds after a peer learned it, and each hop restarts that
  clock, so a remote subscriber can hold a dead publisher's address for a while.
  The data connection carries no topic name -- a subscriber cannot tell it reached
  the wrong publisher -- so handing a recycled port to a DIFFERENT topic would
  deliver one topic's frames under another's name, silently. Stickiness comes from
  the directory itself: a topic's entry holds its port, so a restarting publisher
  reclaims its own, and a stale entry still points where it always meant.
  Allocation is round-robin for the same reason: a freed port is the LAST to be
  handed out again, so reuse takes a full lap of the range.

  Three things to get right:

    * SET IT ON EVERY NODE ON THE HOST, tools included. The range describes the
      machine's firewall, so it is a property of the machine. A node without it
      takes an ephemeral port and is unreachable through that firewall while
      looking healthy everywhere else -- and `qnnt-ls` and `qnnt-cat` start real
      nodes that can win the registry election. A registry holding the role
      without a range answers every publisher "take what you like" and quietly
      un-forwards the whole host. `status` reports `publisher-ports` so this is
      visible rather than inferred. The mirror carries the range to standbys, so
      the role can MOVE to an unconfigured node safely; it cannot help when such a
      node wins the election in the first place, having had nothing to mirror.

    * FORWARD PORTS 1:1. A peer records the address it reached us on, which
      handles a multi-homed host for free -- but it substitutes the HOST only, and
      the port travels verbatim. A rule that shifts ports (external 12300 ->
      internal 2300) tells the far side 2300, and it will dial 2300. This works
      perfectly over WireGuard, which is routed and translates nothing, and fails
      against a port-shifting NAT.

    * A FULL RANGE REFUSES. The publisher does not start, and says so. Falling
      back to an ephemeral port would produce a publisher that works on its own
      host and is unreachable from the network the range exists for.

  This makes qnnt configurable into a firewall or WireGuard setup. It does NOT
  make it traverse NAT: it helps for publishers ON the gateway host, whose ports
  the forwarded range actually reaches. Publishers deeper in the network still
  need routing and forwarding at each level.

  AND IT DOES NOT MAKE THE DATA PLANE SAFE TO EXPOSE. A forwarded range is a hole
  punched straight to sockets that authenticate nobody: whoever reaches them reads
  every message on that host. The range is for the inside of a tunnel, or a segment
  you already trust. SECURITY.txt section 4.

  `docker/federation.sh ports` checks it across six real hosts -- see section 20.

  Language support is the same everywhere -- C, C++, Python and Zig all read the
  same QNNT_* variables and expose the same setters. Python:

    qnnt.Node(federation_port=24202, cluster_key="some-secret",
              peers=["10.0.0.8:2223"])


--------------------------------------------------------------------------------
 8. If something does not work
--------------------------------------------------------------------------------

No output in a subscriber
    Check every terminal is on the same QNNT_REGISTRY_PORT. Different ports mean
    different, isolated systems -- each will work, but they cannot see each other.

Nodes from an earlier run still going
    They hold their topics and keep publishing. Clear them out with:
        pkill -f 'node-c|node-cpp|nodes.py'

Python cannot find the library
    Build it (zig build), and run from the repository root. To point at a specific
    build explicitly:
        export QNNT_LIBRARY=$PWD/zig-out/lib/libqnnt_c.dylib     # .so on Linux

Benchmark numbers look poor
    Build with -Doptimize=ReleaseFast. A debug build carries safety checks that
    dominate the measurement.

A node prints nothing while clearly working
    Only when its output is redirected to a file, and only for Python: run it
    with 'python3 -u'. The C and C++ examples set line buffering themselves.
    Watched in a terminal, all of them print as they go.

Federation does not start
    It needs QNNT_CLUSTER_KEY; without one it prints "federation disabled: no
    cluster key" and stays off. 'status' confirms, reporting either
    "federation off" or the port in use.

Federation says AddressInUse on 2223
    Another node on this machine already holds the default port. Give each one
    its own QNNT_FEDERATION_PORT. Across separate hosts the default is fine.

Federated topics never appear
    Check 'peers' on the node that should be learning them. "down" means it
    cannot reach the peer; a mismatched QNNT_CLUSTER_KEY shows as repeated
    AuthRejected in that node's output.

Real-time worker threads
------------------------

On Linux, QNNT_RT_PRIORITY puts every qnnt worker thread on SCHED_FIFO at that priority,
and QNNT_LOCK_MEMORY pins the process's pages so a page fault cannot stall one:

    QNNT_RT_PRIORITY=40 QNNT_LOCK_MEMORY=1 ./zig-out/bin/qnnt-node-0

The node says so on startup ("worker threads requesting SCHED_FIFO priority 40"), and the
threads can be checked with:

    ps -Lo pid,tid,cls,rtprio,comm -p $(pgrep -f qnnt-node-0 | head -1)

CLS is FF for the workers. The process's own main thread stays TS on purpose -- the library
does not change the scheduling of a thread it did not create. Locking shows up as:

    grep -E "VmLck|VmRSS" /proc/$(pgrep -f qnnt-node-0 | head -1)/status
    grep Mlocked /proc/meminfo        # system-wide, and the honest number

VmLck counts locked address space, most of which is untouched allocator reservation;
Mlocked is the RAM actually pinned, about 10 MB per node. Pages are locked as they are
first touched (MCL_ONFAULT), so warm-up still faults -- run a real-time path once before
trusting its tail.

They need privilege, and different privileges: root, CAP_SYS_NICE or ulimit -r for the
priority; root, CAP_IPC_LOCK or ulimit -l for the locking. Without it the node prints one
line naming the errno and carries on unconfigured, so watch for that line -- the whole
point is a latency bound, and losing it silently would be worse than not asking. Both are
refused outright on macOS, where neither is how real-time behaviour is expressed.

Do not combine it with an unpaced publisher (period 0): that is a busy loop outranking
everything else on its core. The library warns if you ask for both.

Measured effect on an i.MX A53 board, 1 kHz round trip with all four cores contended:

    default priority        p99 5 ms      worst case 47 ms
    SCHED_FIFO 40           p99 128 us    worst case 445 us
    + mlockall              p99 128 us    worst case 170 us

See BENCHMARK.txt B.5 and B.7.


Packing structs, and porting from msgpack
-----------------------------------------

TLD can carry a struct or class directly, the way MSGPACK::pack does, in all four
languages. Run the examples:

    zig build tld-map        C++: TLD_* macros and the msgpack-shaped calls
    zig build tld-map-c      C: a descriptor table
    zig build test           includes both, plus the Zig and Python checks

C++ lists its members once, as msgpack requires:

    struct Reading {
        std::uint8_t channel;
        double value;
        bool valid;
        TLD_DEFINE_MAP(channel, value, valid)     // object, field names as keys
    };
    struct Point {
        double x, y;
        TLD_DEFINE(x, y)                          // array, positional and smaller
    };

    std::vector<std::uint8_t> bytes = qnnt::tld::pack(reading);
    Reading back = qnnt::tld::unpack<Reading>(bytes);

Zig needs no declaration at all -- @typeInfo already knows the fields:

    const got = try tld.unpackFrom(Sample, bytes, arena);   // arena owns the strings
    try tld.packTo(allocator, &buf, sample);

Python uses a dataclass and its annotations:

    data = qnnt.tld.pack(reading)                 # dataclass, Enum, dict, list...
    back = qnnt.tld.unpack(Reading, data)

C describes the struct once as a table, since it has neither templates nor reflection:

    static const qnnt_tld_field reading_fields[] = {
        QNNT_TLD_FIELD(reading, channel, QNNT_TLD_F_U8),
        QNNT_TLD_FIELD(reading, value,   QNNT_TLD_F_F64),
        QNNT_TLD_FIELD(reading, valid,   QNNT_TLD_F_BOOL),
    };
    static const qnnt_tld_desc reading_desc = QNNT_TLD_DESC("reading", reading_fields, 1);

    qnnt_tld_pack_struct(enc, &reading_desc, &value);
    qnnt_tld_unpack_struct_bytes(bytes, len, &reading_desc, &out);

porting from msgpack

    MSGPACK_DEFINE(a, b)          ->  TLD_DEFINE(a, b)
    MSGPACK_DEFINE_ARRAY(a, b)    ->  TLD_DEFINE_ARRAY(a, b)
    MSGPACK_DEFINE_MAP(a, b)      ->  TLD_DEFINE_MAP(a, b)
    MSGPACK_ADD_ENUM(E)           ->  TLD_ADD_ENUM(E)        optional: enums already work
    MSGPACK_BASE(B)               ->  TLD_BASE(B)
    MSGPACK_NVP("k", m)           ->  TLD_NVP("k", m)
    MSGPACK::pack(ss, obj)        ->  qnnt::tld::pack(ss, obj)
    MSGPACK::unpack(p, n)         ->  qnnt::tld::unpack(p, n)     .get().as<T>() unchanged

TLD_ADD_ENUM is a checked no-op: any enum, scoped or not, packs as its underlying integer
without being declared, unlike msgpack which refuses an undeclared one. The macro exists so
a ported file keeps compiling with the line left in. The QNNT_TLD_ prefixed spellings are
identical, for headers that would rather not take an unprefixed macro name.

what the mapping does

  * unknown keys in a frame are ignored, so a producer may add a field without consumers
    being rebuilt; a field the frame omits falls back to its default, and is an error if it
    has none (C leaves it untouched, having no notion of a default);
  * enums travel as integers in every language, so no shared name table is needed. Zig and
    Python also accept a name on the way in;
  * a non-negative integer takes the unsigned encoding whatever the declared type, which is
    a byte shorter for small values and makes all four languages emit the same bytes;
  * `[]const u8` in Zig and std::string in C++ mean text; tld.Bytes and
    std::vector<std::uint8_t> mean a binary buffer;
  * TLD_DEFINE_MAP costs the key bytes and tolerates reordering; TLD_DEFINE is smaller and
    positional, so both ends must agree on the order. The same trade as msgpack's pair.

C cannot express a dynamically sized member, so strings are fixed char[N], buffers are a
fixed array plus a length member, and arrays are fixed length. Anything genuinely dynamic
uses the encoder and iterator API directly, which has no such limit.

lib/testdata/interop.tld is one frame of the schema in examples/tld_map.cpp, and every
language is tested against it: Zig, C++ and Python each decode it AND re-encode it
byte-for-byte, and C decodes it through its descriptor table. That file is the guarantee
that a struct packed in one language is readable in the others -- if a change breaks it,
`zig build test` fails rather than a peer written in another language failing later.


Qt interface (proposal)
-----------------------

include/qnnt_qt.hpp proposes a Qt signal/slot interface shaped after the original Qt/nng
Qnnt class. Qt is not a dependency of qnnt, so the example only builds when told where Qt
is:

    zig build qt-demo -Dqt=/Users/you/Qt/6.10.3/macos

It runs moc over the header and over examples/qt_demo.cpp, links the C ABI, and exercises
the whole path: start a node, publish text and TLD frames, receive both as signals on the
Qt thread, unpack a struct with QString and QList members, stop.

Two design points worth knowing before reviewing it:

  * It is one object with an accessor, not a class you instantiate per component, because
    the library is a process singleton -- one registry role and one queue per process.
  * Messages arrive on qnnt's threads, which are not Qt threads. The interface therefore
    uses the poll queue rather than the callbacks: a worker thread drains it and emits
    through a queued connection, so every slot runs on the receiving object's thread with a
    QByteArray it owns. That also turns one FFI crossing into a batch.

The header carries TLD adaptors for QString, QByteArray, QList, QMap and QHash, so a Qt
model class can be packed by the TLD_DEFINE_MAP macros directly.

What it does NOT declare, because the library cannot do it yet: request/reply
(addResponder, request, requestAvailable), per-topic teardown (removePublisher,
removeSubscriber) and connection-lifecycle signals (publisherConnected and friends). Each
is listed at the bottom of the header with what implementing it would take.


The interop mesh
----------------

examples/mesh/ is five nodes, one per language, all publishing the same struct on their own
topic and receiving it from the other four. Twenty directed links, checked by the nodes
themselves. examples/mesh/SCHEMA.txt is the shared schema and the reasoning behind its
shape.

    node.zig      publishes mesh/zig       node.py       publishes mesh/python
    node.c        publishes mesh/c         node_qt.cpp   publishes mesh/qt
    node.cpp      publishes mesh/cpp

    zig build mesh                                  # zig, c, cpp (python needs no build)
    zig build mesh -Dqt=/Users/you/Qt/6.10.3/macos  # and the Qt node

    QT_PATH=/Users/you/Qt/6.10.3/macos bash examples/mesh/run.sh

Every field of the struct is derived from its sequence number, so a receiver checks exactly
what it should have got rather than merely that something arrived -- and each node exits
non-zero unless it saw a contiguous, correct run from every peer. run.sh collects the exit
codes; a node that was not built is skipped:

    mesh: registry port 22470, 9s, at least 5 samples per peer
    mesh: started 5 node(s): zig c cpp python qt

    === zig: ok ===
    zig: from c        35 samples, seq 10..44, 0 problem(s) ok
    zig: from cpp      35 samples, seq  9..43, 0 problem(s) ok
    zig: from python   40 samples, seq  3..42, 0 problem(s) ok
    zig: from qt       35 samples, seq  4..38, 0 problem(s) ok
    ...
    mesh: every node verified every peer

The sequence ranges start at different points because a subscriber cannot resolve a topic
until the publisher has registered and its own next registry probe comes round. qnnt has no
replay, so those early samples are simply gone; each node therefore requires contiguity from
wherever it attached, not from 1. A gap *inside* a run is a failure.

The five declarations of the struct are independent -- a Zig struct, a C descriptor table,
two C++ classes with TLD_DEFINE_MAP (one using std::string and std::vector, one using
QString and QList), and a Python dataclass. Nothing is generated from anything else; they
meet on the wire. The schema avoids optionals, maps and dynamic strings precisely because C
cannot express them, and a schema only four of the five could carry would not be a common
one.


Connection events
-----------------

A publisher that starts producing before anyone has connected is publishing into nothing:
qnnt has no replay. The library reports connection state so a node can wait for the fact
instead of sleeping for a guess.

six events

    subscriber_connected      a subscriber attached to one of this node's publishers
    subscriber_disconnected   its connection was found broken while publishing to it
    publisher_connected       one of this node's subscriptions attached
    publisher_disconnected    the publisher closed the stream (the subscription retries)
    publisher_stale           nothing has arrived for the stale timeout, if one is set
    publisher_resumed         data arrived on a subscription that had gone stale

Every subscriber_* event carries the topic's current subscriber count, which is what lets a
node wait for a known number of peers rather than merely the first:

    Zig    qnnt.setEventHandler(handler, ctx)      handler(event, topic, peer, subscribers, ctx)
           qnnt.waitForSubscribers(topic, n, timeout_ms)
           qnnt.subscriberCount(topic)
           qnnt.setStaleTimeout(ms)                0 disables it, the default

    C      qnnt_set_event_handler(fn, user)        fn(event, topic, len, peer, len, subscribers, user)
           qnnt_wait_for_subscribers(topic, len, n, timeout_ms)
           qnnt_subscriber_count(topic, len)
           qnnt_set_stale_timeout(ms)

    Qt     subscriberConnected(topic, peer, count) publisherConnected(topic, peer)
           subscriberDisconnected(...)             publisherDisconnected(topic, peer)
           publisherStale(topic)                   publisherResumed(topic)
           waitForSubscriber(topic, ms)            subscriberCount(topic)

    Python node.poll_events(max_events=64)      -> list[Event]
           node.wait_for_subscribers(topic, n, timeout=5.0)
           node.subscriber_count(topic)
           node.set_stale_timeout(ms)

threading, which is the part to get right

Handlers run on the library's own threads -- the publisher's accept thread, a subscriber's
read thread, or whichever thread called publish when a write revealed a dead subscriber --
and two may run at once. They are called with no library lock held, so a handler may call
back in; qnnt_subscriber_count from inside a handler is fine.

The Qt wrapper turns them into signals delivered on the receiving object's thread, through
a queued connection, so a slot sees a QString and a QByteArray it owns and needs no locking.

Python has no callback, deliberately -- a ctypes callback would acquire the GIL on this
node's accept thread, and a Python handler would then hold up the library while it ran. It
drains a queue instead, the same trade `poll` makes for messages:

    for event in node.poll_events():
        if (event.kind is qnnt.EventKind.subscriber_connected
                and event.subscribers >= expected):
            start_publishing()
        elif event.kind is qnnt.EventKind.subscriber_disconnected:
            print(f"{event.peer} left {event.topic}, {event.subscribers} remain")

The queue is filled from the moment the node starts, not from the first poll, so nothing is
lost before a consumer gets around to asking -- which is exactly when the interesting events
happen. It holds 64; past that the newest are dropped and counted in `events_dropped`, so a
consumer that stops draining loses new events rather than the history it has not read.

qnnt_poll_events is in the C ABI too, and either mechanism may be used: a handler for
immediacy, the queue for a language or thread that would rather ask.

what the mesh does with it

Before these existed, every mesh node slept 600-1500 ms before its first message and still
lost the opening samples when a peer was slow to resolve the topic. Now each node knows how
many peers its roster names and waits for exactly that many:

    zig: all 4 subscribers on mesh/zig, publishing
    zig: from c        33 samples, seq 1..33, 0 problem(s) ok
    zig: from cpp      32 samples, seq 1..32, 0 problem(s) ok
    zig: from python   33 samples, seq 1..33, 0 problem(s) ok
    zig: from qt       31 samples, seq 1..31, 0 problem(s) ok

Every one of the twenty links now starts at seq 1, where before most began somewhere between
2 and 10.

Each language uses the mechanism that suits it. The Qt node acts on the signal
(`count >= expecting` in a lambda on subscriberConnected). The Python node drains
poll_events in its main loop, so it also reports peers leaving and topics going quiet. Zig,
C and C++ block on waitForSubscribers, since their startup code can afford to.

One wrinkle worth knowing if you use the scheduler: runPublisher starts its thread ticking
immediately, so waiting in main gates nothing. The gate belongs in the source callback,
which returns null to skip a tick -- and skipping does not consume a sequence number, which
is what keeps seq 1 the first sample anybody sees.


A fake LiDAR, and a QML view of it
----------------------------------

examples/lidar/ is two sensors through one pipeline, in the shape real hardware forces:

    fake-rs16       an RS-LiDAR-16:  750 packets/s, 16 channels, uniform 2 deg spacing
    fake-helios32   an RS-Helios-32: 1500 packets/s, 32 channels, non-uniform spacing
                    -- MSOP and DIFOP over UDP, and no qnnt in either
    rs16.zig        driver for the first generation
    helios32.zig    driver for the Helios
    scan.zig        the vocabulary both drivers produce, so consumers are model-agnostic
    lidar-sensor    the bridge: `lidar-sensor rs16` or `lidar-sensor helios32`
    lidar-viewer    Qt/QML: one binary, either sensor -- it takes the geometry from the
                    stream rather than compiling it in

Swapping the fake for a real RS-LiDAR-16 means pointing the sensor at this host. Nothing
else changes -- the driver binds the same port either way. examples/lidar/SCHEMA.txt has the
packet layout, and is explicit about which parts are datasheet-faithful and which are not.

    zig build lidar                                  # fake sensor + bridge
    zig build lidar -Dqt=/Users/you/Qt/6.10.3/macos   # and the viewer

    ./zig-out/bin/fake-rs16                          # terminal 1: the device
    ./zig-out/bin/lidar-sensor rs16                  # terminal 2: driver + publisher
    ./zig-out/bin/lidar-viewer                       # terminal 3, from the project root

    ./zig-out/bin/fake-helios32                      # or the other sensor, same viewer
    ./zig-out/bin/lidar-sensor helios32
    ./zig-out/bin/lidar-viewer '' lidar/helios32

The rate is the datasheet's, not a convenient fraction of it: 600 rpm, 12 blocks per packet,
32 samples per block, so 750 packets/s and 288,000 points/s. Both ends report it:

    lidar-sensor: RS-LiDAR-16 on lidar/rs16
      600 rpm, 750 packets/s, 288000 points/s
      1552 byte frames vs 1248 on the wire (304 bytes of self-description)

    lidar-viewer: 750 frames/s, 288000 points/s, 30 revolutions, 28661 displayed

28,661 rather than 28,800 because beams that find only sky return a distance of 0, which a
consumer must skip rather than plot at the sensor.

Two decisions in it are worth more than the rendering.

Where the structure stops. A block keeps its azimuth as a named field, because a consumer
wants it without parsing; its 32 samples travel as one BUFFER in MSOP's own layout. Naming
every channel instead would have put ten times more key bytes on the wire than sample bytes.
Self-description is worth 24% here and would not be worth 900%.

Where the work happens. Frames arrive as signals on the GUI thread and are decoded there --
288,000 points/s is a few milliseconds of CPU per second in C++ -- but painting is decoupled:
points accumulate into the revolution being swept, and the item repaints at 30 Hz from the
last completed one. Repainting per packet would be 750 paints/s of a 28,800-point cloud.
QML does layout, chrome and controls; the cloud is a QQuickPaintedItem in C++.

--------------------------------------------------------------------------------
 12. The console tools: qnnt-ls and qnnt-cat
--------------------------------------------------------------------------------

Two commands, split the way the shell splits things: one reports on the bus, one moves data
across it.

    qnnt-ls                     what is published
    qnnt-cat                    the payloads, in or out

That division is not tidiness. `qnnt-ls` writes a report about data and `qnnt-cat` writes
data, and the two want different destinations, different formats and different exit
conditions. One command with a --list flag would have to be two programs wearing one name.

qnnt-ls
-------

    ./zig-out/bin/qnnt-ls                        every topic, one per line
    ./zig-out/bin/qnnt-ls 'lidar/*'              only matching topics
    ./zig-out/bin/qnnt-ls --tree                 grouped by '/' segment
    ./zig-out/bin/qnnt-ls -n                     numbered, for --subs
    ./zig-out/bin/qnnt-ls --subs lidar/helios32  who is subscribed
    ./zig-out/bin/qnnt-ls --subs 3               the same, by its number from -n

    lidar/                      test/
    └── helios32                ├── bench
        └── calibration         ├── topic-a
                                └── topic-b

The trailing slash carries the one distinction a flat list cannot: `lidar/` is not a topic,
only a prefix shared by others, while `helios32` has no slash even though it has a child --
it is a real topic AND a parent, which is what the lidar bridge publishes. Roots carry no
connector, because drawing them as siblings would imply a parent above them that does not
exist.

`--subs` passes the registry's own answer straight through rather than reformatting it. The
registry already lays out subscriber, connected and msgs, and its '#' lines carry the part
that matters most -- whether the publisher has reported at all, which is a different fact
from having no subscribers.

A `--subs` number is resolved against the listing as it stands at that moment, which is why
`-n` prints the numbers beside the names it just fetched: a topic registered or expired in
between shifts every number after it. A name is tried first, so a topic actually called "3"
still works.

qnnt-cat
--------

    ./zig-out/bin/qnnt-cat 'lidar/*'                    decoded, to stdout
    ./zig-out/bin/qnnt-cat --hex test/bench             one hex line per message
    ./zig-out/bin/qnnt-cat --raw test/bench > cap.bin   the frames, verbatim
    ./zig-out/bin/qnnt-cat --publish --raw test/bench < cap.bin     replay it, unpaced
    ./zig-out/bin/qnnt-cat --dump 'lidar/*' > cap.tld   with arrival times and topics
    ./zig-out/bin/qnnt-cat --restore < cap.tld          replay at the recorded pace
    ./zig-out/bin/qnnt-cat --restore --throttle 4 < cap.tld     four times faster
    ./zig-out/bin/qnnt-cat --publish test/notes         each stdin line is a message

    test/bench {"seq":324,"t":1788463155061346,"data":<buffer 6B 000102030405>}
    lidar/helios32/calibration {"model":"RS-Helios-32","rpm":600,"channels":32,...}

Data goes to stdout and notices to stderr, so a redirect or a pipe carries only the payload.
`--raw` writes no topic name, no timestamp and no separator, which is what makes the capture
byte-exact:

    qnnt-cat --max 4 --raw test/bench > cap.bin     # 124 bytes, four frames
    qnnt-cat --publish --raw test/replay < cap.bin  # byte-identical on the far side

It round-trips with no side-channel because a TLD frame carries its own length --
`tld.frameSize` returns null while the bytes so far are only a prefix of one -- so a file of
concatenated frames needs no index. `--hex` round-trips too, and stays hand-editable:
whitespace between pairs is ignored.

capture and restore: --dump and --restore
-----------------------------------------

`--raw` records the payloads and nothing else, and two things are missing from "nothing
else". It does not record when anything arrived, so a replay runs as fast as the pipe
allows -- a 2 Hz stream comes back in under a millisecond. And it does not record which
topic each message came from, so a capture over a glob merges several topics into one
stream that cannot be separated again.

`--dump` wraps each message in a small TLD envelope that carries both, and `--restore`
reads it back:

    { "t": <arrival time, microseconds>, "topic": "<name>", "data": <the payload> }

    qnnt-cat --dump 'test/topic-*' > cap.tld
    qnnt-cat --restore < cap.tld                  # same pace, same topics
    qnnt-cat --restore --throttle 4 < cap.tld     # four times faster
    qnnt-cat --restore --throttle 0.25 < cap.tld  # four times slower
    qnnt-cat --restore test/replay < cap.tld      # redirected to one topic

The pair is named for the operation rather than the payload, and that is the point: one flag
that meant "write envelopes" while reading and "expect envelopes" while publishing was one
flag with two meanings, which is exactly the thing nobody remembers. `--dump` only exists in
the reading direction, `--restore` only in the writing one, and `--restore` implies
publishing -- there is no `--publish --dump` to get the wrong way round.

Restoring needs no topic argument at all: the topics are in the file, and each publisher is
registered the moment its first message appears on stdin. Give a topic and everything goes
there instead, still at the recorded pace.

Measured on a 2 Hz publisher, six messages captured and replayed, gaps at the subscriber:

    --raw replay              0.2, 0.0, 0.0, 0.0 ms    as fast as the pipe allows
    --restore                 500, 487, 513, 501 ms    the recorded cadence
    --restore --throttle 4    129, 121, 129, 124 ms    a quarter of the period
    --restore --throttle 0.5  996, 972, 1038 ms        twice the period
    --dump --throttle 4, then --restore
                              129, 125, 122, 124 ms    scaled at capture instead

`--throttle` is a period DIVIDER, and it works on both sides: 4 makes every interval a
quarter as long, so the stream runs four times faster; 0.25 makes each one four times longer.
On `--dump` it scales the intervals recorded, on `--restore` the intervals waited, and the
two compose -- dumping at 4 and restoring at 0.25 gives the original pace back. It is exact
at 1.0 rather than passing through a float, so a dump taken without it carries the arrival
times it claims to.

An envelope rather than a format of its own, because then a capture is still a stream of
TLD frames: `frameSize` splits it, `qnnt-cat --hex` reads it, and any language with a TLD
decoder can too. The timestamp is when the capturing process received the message, which is
what reproduces the pace actually observed -- a publish time inside someone's payload is
their schema's business, not the envelope's.

Two honest limits. A restore that cannot keep up says so, reporting how far behind the
recorded pace it fell, rather than quietly stretching the stream. And a `--raw` capture fed
to `--restore` is recognised and refused: a payload with its own "t" field would otherwise
be replayed as though those were timings, which is the kind of wrong that looks like it
worked.

Four things about it are decisions rather than accidents:

  * TLD or text is chosen when SUBSCRIBING, not when printing, so it cannot be guessed from
    a topic name -- hence `--text` rather than a heuristic. A TLD frame is length-prefixed
    and its payload contains 0x0A freely; a text topic is newline-delimited. Read a TLD
    topic as text and the newlines inside frames split and join them into garbage.
  * globs read but do not write. A glob matches against the registry's list of topics that
    EXIST, and publishing is how a topic comes to exist, so a wildcard under `--publish` is
    refused rather than quietly matching nothing.
  * `--publish` and `--restore` both take an optional topic -- `--restore test/replay` --
    and only treat the next argument as one when it does not start with '-', so
    `--restore --throttle 4` does not swallow the flag. Topics may also be given positionally,
    which is how one stdin stream fans out to several.
  * `--publish` waits up to `--wait` ms (default 2000) for a subscriber before starting,
    because the alternative is silent loss: a publisher with nobody attached has nowhere to
    put its first messages, and a replay missing its opening frames reads as a corrupt
    capture rather than a race. `--wait 0` skips it.
  * `--max` is enforced in the delivery callback, not in the main loop. The main loop only
    sleeps in short slices waiting to be told to stop, and a 1 kHz topic delivers thousands
    of messages inside one of those slices.

They compose, which was the point of splitting them:

    qnnt-ls 'test/topic-*' | xargs qnnt-cat --text

QUOTE YOUR GLOBS in both. `lidar/*` unquoted is expanded by the shell first, and zsh fails
the command outright when nothing matches on disk. Note also that `*` crosses '/' here,
unlike a shell: `lidar/*` matches `lidar/helios32/calibration` too, which is what makes it
useful on a topic tree.

`zig build ls -- --tree` and `zig build cat -- 'lidar/*'` pass arguments through.

Underneath, discovery is `Qnnt.listTopics` and `Qnnt.registryCommand`: the first asks the
registry for the same table its `list` command prints and reads back the first column, the
second sends any command and hands the reply back verbatim. Both live in the library next to
the code that writes those replies, so a column added or reordered is a local change rather
than a silent break out here.

Glob matching and the tree live in the library for the same reason, and `qnnt-cat` no longer
does its own rescanning: a glob argument is handed to `Qnnt.subscribePattern` (section 13),
which is the same code path a program written against the library gets. What `qnnt-ls` shows,
what `qnnt-cat` reads and what a program joins are one implementation, not three that agree
by inspection.

--------------------------------------------------------------------------------
 13. Subscribing to a glob: bus-style topics
--------------------------------------------------------------------------------

`subscribe` takes one topic name and waits for it. `subscribePattern` takes a glob and joins
every topic that matches -- the ones that exist now, and the ones that appear later.

    Zig     Qnnt.subscribePattern("bus/*", handler, ctx, 500)
            Qnnt.subscribePatternFrames("bus/*", frame_handler, ctx, 500)
            Qnnt.subscribePatternQueue("bus/*", .text, 500)
    C       qnnt_subscribe_pattern("bus/*", 5, cb, user, 500)
            qnnt_subscribe_pattern_frames("bus/*", 5, cb, user, 500)
            qnnt_subscribe_pattern_queue("bus/*", 5, QNNT_QUEUE_TEXT, 500)
    Python  node.subscribe_pattern("bus/*", rescan=0.5)

The matcher itself is reachable, for a program that routes on the topic it was handed or
filters its own traffic back out:

    Zig     Qnnt.topics.globMatch(pattern, topic)
    C       qnnt_topic_matches(pattern, plen, topic, tlen)
    C++/Qt  node->addSubscriberPattern("room/*", QnntNode::Delivery::Frames)
    Python  node.topic_matches(pattern, topic)

Asking the library rather than re-implementing the rules is the point: a program that
disagreed with the library about what "room/*" means would route messages to the wrong
handler while looking correct.

`*` spans any run of characters and `?` exactly one, matched by the same code `qnnt-ls` and
`qnnt-cat` use, so `*` crosses '/' here too: `bus/*` matches `bus/a/b`. The last argument is
how often to look for topics that have appeared since -- milliseconds in C and Zig, seconds
in Python. Zero joins what exists now and then stops looking, which is the right shape for a
one-shot capture and for a process that should not keep polling for ever.

What this buys is the routing of a bus without changing the pub/sub model. If A publishes on
bus/a, B on bus/b and C on bus/c, and each subscribes to `bus/*`, then everything any of them
publishes reaches the other two -- with no broker, no new wire protocol, and no change to how
publishing works. Each node is still a set of publishers and a set of subscriptions; the
pattern only saves it from having to be told the names in advance.

Four things are worth knowing before reaching for it.

  * It is a SEPARATE call, not `subscribe` noticing a '*'. A pattern costs a poll of the
    registry and a connection per match, and neither should be something a caller gets by
    accident because a topic name happened to contain a star. Programs that do not ask for
    it pay nothing -- no extra thread, no extra traffic.
  * Fan-out is per publisher, not per pattern. Matching ten topics opens ten connections. A
    symmetric arrangement where N nodes each read the others is N(N-1) connections: 6 for
    three nodes, 2450 for fifty. This gives the ROUTING of a bus, not its economics. The cap
    is 256 topics per pattern, and hitting it says so on stderr rather than silently
    stopping.
  * Discovery is polled, not pushed. The poll is cheap -- it asks the registry for its
    directory version and lists the topics only when that has moved -- but a new topic is
    joined within the rescan interval, not instantly.
  * Matching means matching. A node's own topics match its own pattern, and it will subscribe
    to itself. That is deliberate rather than special-cased: every handler is already given
    the topic name, so a node that wants to skip its own traffic says so in one line, while a
    logger or recorder that wants everything would have had to fight a built-in exclusion.

The handler is the ordinary one. Its first argument is the topic the message came from, which
is what makes a single handler enough for a whole pattern -- and, on the queue path, what lets
one queue carry every matching topic with no extra bookkeeping.

Running examples: `python/demo.py` and `examples/node_demo.c` each end with a glob section
that joins a topic present at the start, a topic created afterwards, and refuses a near miss.

--------------------------------------------------------------------------------
 14. A depth camera on the same four layers: examples/zed/
--------------------------------------------------------------------------------

The LiDAR chain again, for a ZED X stereo camera, so the structure can be compared
side by side:

    fake_zed.zig   produces frames at native resolution (no qnnt)
    shm.zig         the handoff: a ring of frame slots in shared memory
    zed.zig        the driver: read, validate, calibrate
    frame.zig       the model-independent vocabulary and the deprojection
    camera.zig      the qnnt node: TLD, three topics
    viewer.cpp      Qt/QML: the mono image and depth, colourised

    zig build zed -Dqt=/path/to/Qt/6.10.3/macos
    ./zig-out/bin/fake-zed        # terminal 1
    ./zig-out/bin/camera-sensor    # terminal 2
    ./zig-out/bin/camera-viewer    # terminal 3, from the project root

    camera/
    └── zed2i/
        ├── calibration     intrinsics AT THE PUBLISHED SIZE, ~1 Hz
        ├── cloud           the frame deprojected, subsampled
        ├── depth           u16 millimetres + a mono image
        └── sensors         IMU, barometer, magnetometer at 400 Hz (ZED 2i only)

Two cameras, one driver: a ZED X at 1920x1200 and a ZED 2i at 1920x1080 with an IMU,
barometer and magnetometer. The LiDAR needed two drivers because an RS-16 and a Helios speak
different wire formats; two ZEDs are the same two SDK calls with different parameters.

    ./zig-out/bin/fake-zed --model zed2i            # native 1080p, 187 MB/s of UDP
    ./zig-out/bin/camera-sensor --model zed2i --scale 4
    ./zig-out/bin/camera-viewer '' camera/zed2i

The fake transmits at NATIVE resolution and the bridge decides how much to publish, which is
what makes the bandwidth decision visible:

    --scale 1    1920x1080   186.6 MB/s    loopback only
    --scale 4     480x270      11.7 MB/s   comfortable anywhere      <- default

Both ceilings are measured in BENCHMARK.txt: loopback carries 1426 MB/s, gigabit 117.6. The
bridge prints which side of that line the chosen scale falls on.

The camera-to-driver handoff is SHARED MEMORY, not a transport, because that is what the ZED
SDK is: `retrieveMeasure()` hands you a pointer into a buffer. A ring of frame slots in a
shared mapping reproduces it -- the producer never blocks, and a slow driver misses whole
frames rather than receiving damaged ones, which is what happens when an application is late
to `grab()`.

It took three attempts to get there and the discarded ones are documented in
examples/zed/SCHEMA.txt, because the reasons are the useful part: UDP chunking made the
driver reassemble 760 datagrams and model packet loss that does not exist, and a named pipe
would have lock-stepped the camera to the reader through a 64 KB buffer -- throttling the
sensor, which real hardware cannot do. Measured through shared memory: 120 frames a second
of 6.2 MB frames, 746 MB/s, zero loss.

Supporting 1080p meant fixing a library bug worth knowing about independently. The TLD
subscriber capped a frame at 1 MiB while the publisher had no limit at all, so a producer
could emit frames every subscriber refused -- and refusal is not graceful: the read loop
breaks and reconnects into the same frame forever, while the producer sees nothing wrong.
The cap is now 16 MiB, applies to both ends, and is settable per node with
QNNT_MAX_FRAME_BYTES.

One thing is NOT like the LiDAR chain, and examples/zed/SCHEMA.txt says so at the top. The
LiDAR fake reproduces a wire that exists -- and this repository's version of it was
corrected against real hardware. A ZED X has no network protocol: it runs GMSL2 into a
capture card and is read through the ZED SDK, so the framing in zed.zig is INVENTED and
stands in for that SDK boundary. Everything from the driver's output onwards is a faithful
analogue; that one seam is not, and porting to a real camera means replacing it with
sl::Camera calls and keeping the rest.

What the chain does exercise, and what a real camera would exercise identically: reassembling
a 200-datagram frame, counting the rows that never arrive, refusing intrinsics that would
produce a plausible-looking cloud out of nonsense, and telling a consumer whether the
calibration came from the camera or from the driver's nominal defaults. The fake also drops
about 6% of every frame's depth, moving between frames -- because a stereo camera does, and
a consumer written against a gapless depth map falls over on the first real frame.

A real ZED 2i can drive it, on macOS, with one command changed:

    zig build zed -Duvc -Doptimize=ReleaseFast
    ./zig-out/bin/zed-uvc                    # the camera, instead of fake-zed
    ./zig-out/bin/camera-sensor --model zed2i --scale 1
    ./zig-out/bin/camera-viewer '' camera/zed2i

The bridge reads the shared region and never grabbed from a camera, so only the producer
changes. Measured on real hardware: 15 frames/s, 672x376, 0 missed. Two things it cannot
give you -- depth and the IMU both come from the ZED SDK, which has no macOS build, so the
mono plane is the real left image and the depth plane is zero. That also exposed a driver
bug: the fallback intrinsics came from the spec table's 1920x1080 rather than the 672x376
actually arriving, and would have put every point out by 2.86x.

See examples/zed/SCHEMA.txt for the wire format, the published schema, the geometry and
what it would take to point this at real hardware.

--------------------------------------------------------------------------------
 15. Driving a real robot: examples/ugv/
--------------------------------------------------------------------------------

A UGV Beast on one side, qnnt topics on the other, and a Qt/QML control station
on the end of them:

    sio.zig      Socket.IO over its HTTP long-polling transport
    beast.zig    the robot's command and telemetry vocabulary, read from the robot
    mjpeg.zig    JPEG frames out of the robot's chunked multipart video stream
    bridge.zig   the qnnt node: three topics subscribed, three published
    pilot.cpp    Qt/QML: one movement pad, live video, lights, watchdog indicator
    main.qml     the interface

    subscribes   <prefix>/drive   <prefix>/gimbal   <prefix>/lights
    publishes    <prefix>/telemetry  <prefix>/status  <prefix>/camera

VIDEO GOES OVER A TOPIC, not from the robot's web server. The bridge stays the only
thing that talks to the robot, so the station works from anywhere the topic reaches --
including across a federation link, from a machine that cannot route to the robot at
all. `--no-video` turns it off for a controller that wants telemetry and none of the
bandwidth; a frame is about 15-20 KB.

The stream needs no multipart parser, which is worth knowing before you write one.
`GET /video_feed` is `multipart/x-mixed-replace` inside `Transfer-Encoding: chunked`,
and a part carries NO Content-Length -- so the end of a frame has to be found. Finding
it via the next boundary would put every frame one frame behind. JPEG delimits itself
instead: SOI (FF D8) to EOI (FF D9), unambiguous because a literal FF inside entropy-
coded data is always stuffed as FF 00. That also skips the part headers for free, since
they are ASCII and ASCII has no FF. The chunked layer, by contrast, must be decoded
properly: its size lines are ASCII hex and would otherwise be spliced into a frame.

THE LIGHTS CYCLE, they do not set. The robot exposes no absolute level for either the
chassis light or the head light, so `<prefix>/lights` takes {{base, head}} booleans and
each one advances that light a step -- exactly what pressing the button on the robot's
own web UI does. The resulting brightness comes back as base_light and led_mode on the
telemetry topic, so the buttons show what the robot reports rather than what was asked.

They also go on a different channel from everything else: drive and gimbal are
`{{"T":<n>,...}}` JSON on the /json namespace, while the lights are UI action codes on
/ctrl, sent as `{{"A":<code>,"B":0,"C":0}}` -- and as a JSON *string*, because the UI
calls socket.send(JSON.stringify(...)) and Socket.IO's send is emit("message", x). The
codes come from the robot's own config, like the T numbers.

ONE MOVEMENT CONTROL, SWITCHED. The pad drives the rover or aims the camera arm,
selected by the ROVER/CAMERA switch above it. The alternative -- a pad for the rover and
preset buttons for the arm -- could only jump the arm to fixed angles, and aiming a
camera means watching the picture and moving until it is right, which is what a pad is
for. Two deliberate differences between the modes:

  * switching mode STOPS THE ROVER first, in both directions. Leaving for the camera
    with a track command standing would drive the robot with a control no longer
    pointed at it. The deadman would catch it in half a second; a mode switch should
    not depend on a watchdog.
  * the rover pad springs back to stopped when released, the camera pad HOLDS its aim.
    A vehicle that keeps moving when you let go is the failure this bridge exists to
    prevent; a camera that snapped back to centre could never be pointed at anything.

Space still stops the rover in both modes -- it is a reflex, and it should not mean
something else because a switch is set. Centring the arm is its own button.

    zig build ugv -Dqt=/path/to/Qt/6.10.3/macos
    ./zig-out/bin/ugv-bridge --host 192.168.50.5:5000   # terminal 1
    ./zig-out/bin/ugv-pilot                             # terminal 2

    ugv/beast/drive       subscribed   {left, right} in [-1, 1]
    ugv/beast/gimbal      subscribed   {pan, tilt} degrees, absolute
    ugv/beast/telemetry   published    battery, angles, CPU -- about 0.2 Hz
    ugv/beast/status      published    the link, the robot's limits, the watchdog

Unlike the LiDAR and camera chains there is NO FAKE here. A fake that accepted
drive commands and did nothing would be a worse test than none: the whole risk in
this example is that a command reaches an actuator when it should not, and a
simulator cannot exercise that.

Almost nothing about the protocol is guessed. The robot serves its own
configuration at GET /config, and that file defines the vocabulary:

    fb:                   the telemetry field map -- base_voltage: 112, so
                          {"112":1201} is 12.01 V
    cmd_movition_ctrl: 1  (the robot's spelling)
    cmd_gimbal_ctrl: 133
    args_config:          max_speed: 0.5 -- the ceiling the vendor's own UI uses

beast.zig parses it, so a firmware that renumbers a field or raises a limit is
followed rather than fought. examples/ugv/testdata/config.yaml is the real file
from a real robot, kept as a test fixture, because the SHAPE of that file is part
of the protocol: the first parser read a flat file, the real one is nested one
level under section headers, and nothing but the real bytes would have caught it.
`from_robot` means "the values were found", not "the file downloaded" -- reporting
the robot's limits while enforcing built-in ones is the failure worth preventing.

WHY SOCKET.IO OVER POLLING. The robot speaks Socket.IO, not raw WebSocket. Its
default transport is a WebSocket, but the protocol begins every session on long
polling and a client that never upgrades stays a first-class client -- and that
lower rung is plain HTTP, which std.http.Client already gives us. No WebSocket
implementation, no dependency. Measured cost: 11-24 ms per command, which is
nothing at the rate a teleoperated robot needs.

THREE CLOCKS, and they answer three different questions:

    --rate 10        the MAXIMUM send rate. A controller streaming faster is
                     coalesced; the newest setpoint wins, because a stale velocity
                     command is worthless and executing a backlog is dangerous.
    --heartbeat 500  how often an UNCHANGED setpoint is re-sent. The vendor's UI
                     re-sends every 2000 ms, which says the firmware stops the
                     tracks if commands stop arriving.
    --deadman 500    how long a setpoint may go un-refreshed before it becomes a
                     stop.

The first version sent every cycle at --rate, which is the textbook shape and was
wrong here: each command is an HTTP POST, and 10 POST/s is ten times what the
vendor's own UI sends over a cheaper transport. Send-on-change plus a heartbeat is
both lighter on the robot and MORE responsive -- a change goes out within one 5 ms
tick instead of waiting out a period.

TWO INDEPENDENT STOPS, because they cover different failures:

    1. The bridge's watchdog. No drive command for --deadman ms and the setpoint
       is forced to zero, which the loop then keeps sending.
    2. The robot's own firmware timeout, if the bridge itself dies.

(1) exists because (2) is slower and outside our control. A controller that
crashes mid-turn, a Wi-Fi drop, a GUI that freezes -- all leave a robot driving
until something stops it, and 500 ms of unintended motion is a very different
event from three seconds of it. Verified with kill -9 on the GUI: the watchdog
tripped and held 0/0.

The GUI is the other half of that contract. It publishes at 10 Hz whether or not
anything changed, so the watchdog's silence is meaningful; a controller that
published only on change would be indistinguishable from a crashed one the moment
the operator held a steady speed. It also releases every key when the window loses
focus, because a key-up is never delivered to an unfocused window and a latched key
would keep the robot driving after the operator switched away.

WHAT A DAY WITH REAL HARDWARE ACTUALLY FOUND. Four defects, none of which a
simulator would have shown, and two of them were mine misreading the evidence:

  * Commands never arrived at all. The subscription used text delivery, which waits
    for a newline delimiter that binary TLD never contains -- so the handler was
    never called and nothing reported why. The bridge now counts and prints
    undecodable commands rather than swallowing them.
  * Both loops hung indefinitely. std.http.Client has no read deadline, so when a
    routing change on the host sent packets out a second interface, every request
    sat in receiveHead until TCP gave up -- about fifteen minutes. The watchdog
    lives on one of those loops, so it stopped running too, which is precisely the
    failure it exists to prevent.

    Fixing it took two attempts. Setting SO_RCVTIMEO on the client's socket does
    not work: the timeout then surfaces as EAGAIN, and Io.Threaded's read path
    treats EAGAIN as a programmer bug and panics -- which turned a hang into a
    crash on shutdown. Io's own receiveTimeout is the supported way to bound a
    read, and it needs the socket in hand, so sio.zig now speaks HTTP/1.1 directly
    over an Io.net stream and std.http.Client is gone. That is small because of
    what the robot does: every response is Transfer-Encoding: chunked with
    Connection: close, so there is no connection to pool and no length to
    negotiate, and the body is everything up to EOF once the chunk framing comes
    off. The deadlines are 1500 ms for a command and 35 s for a long poll that
    legitimately waits.

  * The connect was the worst of it, and it took a third attempt to see. Passing a
    connect deadline makes Io.Threaded panic with "TODO implement
    netConnectIpPosix with timeout" on Zig 0.16, so a connect was bounded only by
    the OS's SYN retransmission. Measured against a silent host on this subnet:
    76.6 seconds for ONE attempt, with both loops frozen for all of it -- and
    since the robot is its own access point and reboots without notice, that was
    the cost of every reconnect. sio.zig now connects straight through libc, a
    non-blocking connect followed by poll with a real deadline, then puts the
    descriptor back into blocking mode before Io ever touches it (Io's read path
    treats EAGAIN as a programmer bug -- the same trap that made SO_RCVTIMEO
    unusable). Same test: 76.6 s -> 6.1 s, and the bridge keeps publishing status
    at its normal 500 ms cadence throughout, reporting link=false instead of
    going silent.
  * The watchdog was on the wrong thread. It lived in the output loop, which is
    the loop that can be inside an HTTP round trip -- so a 500 ms deadman could go
    up to 76 s without being evaluated, absent exactly when it was needed. It now
    runs on the supervisor thread, which does nothing but publish and sleep 20 ms.
    It still cannot make the robot stop by itself, only the output loop sends; what
    it guarantees is that the setpoint is already zero the instant the deadman
    expires, so whatever goes out next is a stop, and the status topic tells the
    truth in the meantime.
  * A lost session was permanent. Three consecutive poll failures now rebuild it.
  * This robot's Wi-Fi reboots without notice -- it is its own access point, so the
    host drops off the network with it. Two consequences, both now handled: a
    failed first connection is NOT fatal (the topics still come up and the poll
    loop keeps retrying, so the status topic can report the link down rather than
    the process just exiting), and GET /config is re-read on every session
    (re-)establishment. Read once, a bridge started while the robot was rebooting
    would enforce built-in limits for the rest of its life while the robot sat
    there able to state the real ones. It reported that honestly, but reporting is
    not recovering.
  * Telemetry arrives at about 0.2 Hz. This is the ROBOT's cadence, not congestion:
    measured on a clean session with nothing else connected, and request_data does
    not pull one on demand either. Two wrong readings preceded that measurement --
    first blaming command load, then blaming a wedged server when the truth was the
    routing change above. The GUI shows the age of the reading for this reason: a
    five-second-old number looks broken when it is not.

WHAT IS UNVERIFIED. The gimbal. This robot's /config reports module_type 0, so no
pan-tilt module is configured and the robot ignores T:133 -- pan_angle stays pinned
at 0 whether the command comes through qnnt or straight from curl. The command path
is complete and the UI keeps its pan-tilt row, but nothing here has moved a gimbal.
Setting module_type is a change to the robot's own configuration, not this
bridge's, so it is left to whoever owns the machine.

Drive commands were confirmed to reach the robot end to end; there is no wheel
feedback in the telemetry map, and battery sag on a suspended robot proved too
small to measure, so "the tracks turned" rests on the operator watching them.

 16. A home full of sensors: examples/dirigera/
--------------------------------------------------------------------------------

An IKEA DIRIGERA hub on one side, qnnt topics on the other:

    tls_openssl.zig  TLS, because std's client cannot reach this hub (see below)
    https.zig        HTTPS with the chain verified against IKEA's embedded root
    hub.zig          the hub's vocabulary, read off a real hub
    ws.zig           enough of RFC 6455 to listen to the push stream
    pair.zig         the pairing exchange: PKCE, and the hub's button
    bridge.zig       the qnnt node: three topics published, two subscribed
    home.cpp         Qt/QML: rooms, lights, sensors, and the pairing panel
    main.qml         the interface

    zig build dirigera -Ddirigera-openssl=/opt/homebrew/opt/openssl@3 \
                       -Dqt=/path/to/Qt/6.10.3/macos
    ./zig-out/bin/dirigera-bridge --host 192.168.1.20:8443 --pair    # once, ever
    ./zig-out/bin/dirigera-bridge --host 192.168.1.20:8443 --list    # a diagnostic
    ./zig-out/bin/dirigera-bridge --host 192.168.1.20:8443           # the bridge
    ./zig-out/bin/dirigera-home                                      # the station

    home/dirigera/state       published   one frame per device, when it changes
    home/dirigera/inventory   published   every device, on a timer
    home/dirigera/status      published   the link, the hub, the counters, pairing
    home/dirigera/light       subscribed  {id, on?, level?, kelvin?}
    home/dirigera/pair        subscribed  {name, cancel} -- start or stop pairing

THIS ONE PUSHES, and that is the point of it. The hub holds a WebSocket open and
sends state the moment a light is switched or a sensor trips, so the bridge is a
translator rather than a poller. Compare the UGV in section 15, which had to be
asked and answered about every five seconds. `--list` exists only as a
diagnostic; the running bridge never polls for state.

The inventory is still refetched on a timer, for a different reason: the push
stream carries CHANGES, so a device that never changes would never appear and a
late subscriber would see an empty world. The timer makes the topic complete
rather than merely current -- the same reason the camera bridge republishes its
calibration.

Find the hub the way it advertises itself, rather than hardcoding an address that
moves:

    dns-sd -B _ihsp._tcp local              # -> gw2-<serial>
    dns-sd -L gw2-<serial> _ihsp._tcp local # TXT: ipv4address, type, sv, pv

PAIRING, which is where this example starts rather than something you arrange
beforehand. Every call but one needs a bearer token, and the only way to get one
is an OAuth2 PKCE exchange finished by pressing the hub's physical action button:

    GET  /v1/oauth/authorize?audience=homesmart.local&response_type=code
                            &code_challenge=<S256>&code_challenge_method=S256
         -> {"code": "..."}      and opens a pairing window on the hub
    ... press the action button on the underside of the hub ...
    POST /v1/oauth/token    (form: code, name, grant_type, code_verifier)
         -> {"access_token": "..."}

On firmware 2.975.3 the methods are the REVERSE of most published examples:
authorize is a GET -- POSTing it is a 404 -- and token is a POST. Getting it
backwards produces a 404 that reads like a wrong path, which sends you looking in
entirely the wrong place.

Two ways in, both running the same code in pair.zig:

    dirigera-bridge --host <ip:port> --pair     # on the terminal
    dirigera-home                               # the pairing panel

The bridge used to read a token from a file and EXIT if it was missing, which left
the procedure in a script outside the tree -- the example could not be run from a
clean checkout. Now an unpaired bridge still starts: its topics come up, its
status carries `paired: false`, and it waits for a request on the pair topic. The
GUI covers the house with a pairing panel until that flips, so the first run of
the whole example is: start the bridge, start the station, press the button.

The panel shows the bridge's running commentary rather than a spinner, because
the hub's refusals carry the one fact a person standing at it cannot guess. The
hub allows ONE pairing window at a time and answers a second with "Already one
ongoing pairing request" -- so a stray probe of the authorize endpoint locks out
the next attempt until it lapses, which is exactly what happened while this
protocol was being worked out. "Invalid authorization code" means the opposite:
the window is yours and the button has not been pressed yet. A spinner says
neither. The flow waits the first out and keeps polling through the second.

WHAT THE REAL HUB CORRECTED, after all of the above passed offline. Two bugs,
and neither could have been found without the device:

  * The waiting reply was measured wrong. Probing the token endpoint with a
    MADE-UP code answers "Invalid authorization code", and that had been taken for
    what an unpressed button looks like. It is not. A real, live code with the
    button unpressed answers

        403 {"error":"Button not pressed or presence time stamp timed out."}

    so the flow classified the ordinary waiting state as a dead window and
    reopened the pairing on every poll -- churning through windows seconds apart
    while nobody was given time to press. The lesson generalises: a dummy value
    exercises the error path, not the waiting path, and those are different
    sentences. Both strings are now pinned in the tests, verbatim.
  * `--pair` segfaulted on its first call. It used `qnnt.nowMicros()` and
    `qnnt.sleepMs()`, which go through the LIBRARY's `Io` -- valid only after
    `qnnt.run()`. `--pair` never starts a node, exactly like `--list`. This file's
    own header warns about that trap for the token read and `--list`; pairing was
    the third thing outside a running node and walked straight into it. The
    callbacks use `bridge_io`, which is valid from the first line of `main`.

Paired against the real hub afterwards, with the retry logic plainly earning its
keep: a window lapsed, a second was refused with "Already one ongoing pairing
request" because the first still held the slot, a third opened, and the press
landed on that one. The token then listed 17 devices and brought the push stream
up, so it is accepted on both the REST and WebSocket paths.

THE EXCHANGE IS TESTED WITHOUT A HUB. pair.zig takes its HTTP, clock, sleep and
entropy as callbacks, so it imports nothing -- not even the TLS client -- and the
whole state machine runs against a fake hub in `zig build test`: the button
pressed late, the window lapsing and reopening, another client holding the slot,
a dead code, a cancel, and giving up. The PKCE derivation is checked against RFC
7636's published vector, which matters because a padded or non-url-safe challenge
is still a plausible 43-character string and the hub would simply reject every
pairing without saying why. None of that could be exercised through a real client:
it would need a hub on the bench and a finger on its button for each case.

WHY OPENSSL, in a repository that otherwise has no dependencies. Zig 0.16's
`std.crypto.tls.Client` cannot complete a handshake with this hub, and the gap is
narrow: the hub is TLS 1.2 only (forcing 1.3 returns alert 70), its certificate
is ECDSA, and it accepts only ECDHE-ECDSA cipher suites -- while std offers only
ECDHE_RSA for TLS 1.2. The ECDHE_ECDSA constants exist in
`std.crypto.tls.CipherSuite` and are never offered, and the offer list is a
private comptime constant. Everything else in std is present; ECDSA signature
verification is implemented and advertised. So one list is the whole obstacle.
The alternative was vendoring 1700 lines of the standard library to change three
enum entries. `-Ddirigera-openssl=` follows the same convention as `-Dqt=` for
the Qt viewers, and `zig build test` still passes without it -- only the three
tests that link OpenSSL are skipped.

CERTIFICATE VERIFICATION IS REAL HERE, which is worth stating because every
published DIRIGERA client disables it. The hub presents its whole chain, four
deep, ending in a self-signed root; that root is embedded as
`ikea_root_ca.der` and is the only trust anchor -- not even the system store is
trusted. What is NOT verified is the hostname, and that is unavoidable: the leaf
carries no subjectAltName and its CN is a device serial, so there is nothing to
match an address against. `SSL_set1_host` is therefore deliberately never called,
which gives chain verification without name verification.

THREE THINGS ABOUT THIS API worth knowing before writing against it, all learned
from the hub rather than from documentation:

  * `202 Accepted` means QUEUED, not applied. A PATCH to an unreachable device
    succeeds and nothing happens. A command is never a confirmation.
  * Only `capabilities.canReceive` is writable. For lights that is isOn,
    lightLevel and colorTemperature; for remotes and sensors it is customName
    alone, which makes them read-only in every way that matters. hub.zig reads
    that list rather than inferring from the device type.
  * `colorTemperatureMin` is numerically LARGER than `colorTemperatureMax` --
    4000 against 2202 on the same bulb, names in mired order and values in
    Kelvin. A clamp written the obvious way yields an empty range and rejects
    every input, so `clampTemperature` sorts the bounds instead of trusting their
    names.

THE STATION is the fourth in this repository, after lidar-viewer, camera-viewer
and ugv-pilot, and the one with the least in common with them: nothing in it is a
render loop. A LiDAR viewer redraws a million points a second; a home has
seventeen devices that change when somebody walks past a sensor. So it is a model
following a push stream.

IT IS ORGANISED BY FUNCTION, not by location, and that was a correction. The
first version grouped everything by room, which is the obvious reading of a hub
whose devices each carry a room -- and it put a lamp, an occupancy sensor and a
light meter in one list. Those answer three unrelated questions: what can I
switch, is anyone there, how bright is it. Room is still shown; it is a label
rather than the axis.

    lights     actuators, grouped BY ROOM inside the section -- because that is
               genuinely how you think about lights -- with the controls the hub
               says it will accept
    presence   occupancy. Motion is an EVENT, so the row shows when it last fired,
               not what the sensor reads at this instant. The hub clears
               isDetected on its own schedule, so a strict reading flickers; the
               dot holds for thirty seconds.
    remotes    inputs. Nothing to operate, and the only actionable fact is battery.

ONE PHYSICAL SENSOR, ONE ROW, which needed a change to the bridge. A VALLHORN is a
single unit on the wall that the hub reports as TWO devices -- a motion sensor and
a light sensor -- joined only by a shared `relationId`. The bridge had not been
publishing that field, so the station could not tell them apart from two separate
sensors, and the light-sensor halves showed up as nameless roomless rows (they
carry neither of their own). With `relation` published, the light meter is folded
into its twin's row as a reading, and the seventeen devices become thirteen rows:
five lights, three sensor UNITS rather than six devices, five remotes, with the
gateway and the three folded-in meters not shown at all. A light sensor with no
motion twin still gets its own row, since then it really is a standalone meter.

Three further things come from the topics rather than from assumption:

  * WHICH CONTROL TO SHOW comes from the hub. A light gets a switch only if the
    hub accepts isOn, a brightness slider only for lightLevel, a warmth slider
    only for colorTemperature, over the bulb's own Kelvin range. None of it is
    inferred from the device type, because the type does not determine it -- a
    dimmable white bulb and a tunable one are both `light`. This is why the bridge
    publishes can_set_on / can_set_level / can_set_temperature separately rather
    than one `controllable` flag: the GUI needed the specifics, and the hub is the
    only thing that knows them.
  * A COMMAND IS NOT A CONFIRMATION. The hub answers 202 and applies the change
    asynchronously, or not at all for an unreachable device. So a switch does not
    move when clicked -- it moves when the state topic says the light changed. The
    click marks it pending with a blue edge, and a pending change that never
    arrives stays visible for four seconds instead of being quietly forgotten.
  * UNREACHABLE IS NOT OFF. Those rows are dimmed and labelled, because the hub
    reports last-known state for a device it cannot reach -- for one bulb here, a
    lightLevel of 100 from eight hours earlier. Showing stale state as current is
    the whole failure mode of a home dashboard, so every row also carries the age
    of its last report.

"All on" and "all off" are per ROOM and there is deliberately no whole-house
version: one button that switches off somebody's entire home is a mis-click
waiting to happen.

There is no watchdog, and that is a decision rather than an omission. The UGV
needed one because a robot left driving is dangerous; a light left on is not, and
a bridge that switched lights off when its controller went quiet would be a worse
failure than the one it prevented. The bridge sends nothing at startup and
nothing periodically -- only what arrives on the command topic.

examples/dirigera/testdata/devices.json is a real hub's `/v1/devices`, SANITISED:
it came out of somebody's home, so the serial numbers, timezone and room names
are replaced. What the tests need is the shape, and every structural property
survives -- the five device types, the canReceive lists, the paired sensors
sharing a relationId, an unreachable device, and the temperature quirk above.

FOUR BUGS THIS COST, three of them mine and all in the same layer -- the seam
between OpenSSL and Io:

  * `Io.Writer.drain` must write the already-buffered bytes AND the caller's
    vectors, in one call. Writing only the buffered part silently truncated every
    request: the trailing "\r\n" of each header block sat in `data`, never went
    out, and the hub waited for a request that never finished, then closed.
  * `Io.Reader.readVec` must advance `end` for bytes that land in the reader's
    own buffer rather than returning them as consumed. `peekGreedy` passes no
    buffers of its own, so EVERY byte is internal; returning the count made the
    reader look empty after a successful read, which read as end-of-stream and
    turned a good 308-byte response into nothing.
  * `takeDelimiterExclusive` does not consume the delimiter, so every second
    line read as blank. The WebSocket handshake took the first blank line as the
    end of the headers and failed for want of a Sec-WebSocket-Accept it had never
    looked at. `takeDelimiterInclusive` is what a line reader wants.
  * A read failure must not be treated as a complete body. `catch break` on the
    response loop turned a transport fault into a silently empty response, which
    is the same class of mistake as the first two: an error path quietly
    producing plausible data.

--------------------------------------------------------------------------------
 17. Federation topologies: examples/federation/
--------------------------------------------------------------------------------

What a federated registry converges to when the peers are wired four different
ways:

    node.py          one site, or one app on a site
    topologies.py    the harness: four checks across four topologies

    python3 examples/federation/topologies.py            # all of it, ~5 min
    bash docker/federation.sh                            # the same four, on real hosts
    python3 examples/federation/topologies.py converge
    python3 examples/federation/topologies.py clocks --forget   # adds a 5 min wait

Six sites, each a separate process with its own registry port and its own
federation port -- several fit on one machine because the registry is host-local
by design, so here "host" means "registry port". A topology is then nothing but a
set of QNNT_PEERS lists:

    star    B,C,D,E all dial A. A dials nobody.
    ring    A->B->C->D->E->A
    mesh    every site dials every other
    hybrid  A=B=C meshed, D dials A, E dials D -- a chain hanging off a mesh

SITE Z IS THE CONTROL and it is what makes the rest mean anything: it carries the
cluster key, has no peers, and nobody dials it. It must see only its own topic and
nothing may see its topic. Without it, "every site sees every topic" would equally
be the result of every probe accidentally reading one shared registry -- the
easiest way for a test like this to pass while proving nothing.

RESULT: all four topologies converge to the same directory, and all four deliver.

                     converged   delivery at 2 hops   survives one death
    star               0.4s            yes              NO  -- hub is the SPOF
    ring               0.7s            yes              yes -- becomes a chain
    mesh               0.4s            yes              yes
    hybrid             0.4s            yes              partly -- leaf cut off

Four things this established that are not obvious from the source:

A ONE-WAY PEER LIST GIVES TWO-WAY VISIBILITY. In the star the hub dials nobody,
yet it sees every leaf, and the leaves see each other through it. An exchange
pushes the local entries and then pulls the peer's over the same connection, so
expected reachability is the transitive closure over the UNDIRECTED graph. That
matches what addPeer's doc claims -- "peer lists need not be symmetric or
complete" -- and it is why the star works at all with the hub unconfigured.

CONVERGENCE IS EAGER, NOT ON THE TIMER. The sync interval is 5s, but every
topology converges in well under a second because a change is pushed when it
happens. The ring took 2.7s when this was written, which looked like the honest
cost of relaying one hop at a time; it was a missing notification on the inbound
path, and section 20 records the chase. It is 0.7s now.

FEDERATION IS A CONTROL PLANE, NOT A DATA PLANE. Delivery is identical at one hop
and two -- 77 to 78 messages in an 8s window at 10 Hz either way. In `hybrid`,
where E reaches A only through D, the subscriber at E connects to port 49788,
which is A's OWN publisher socket. D carried the address and nothing else, so it
cannot bottleneck the data and its death cannot interrupt an established
subscription -- only the ability to learn about new topics.

TOPOLOGY ONLY MATTERS WHEN SOMETHING DIES. On the happy path all four look
identical, so the difference has to be measured by killing a site and then
publishing something NEW at a survivor -- which isolates connectivity from expiry:

    star, hub killed        nobody learns it. Every leaf's only peer is gone.
    ring, one site killed   all four survivors learn it; the loop is now a chain.
    mesh, one site killed   all four learn it.
    hybrid, joint killed    the meshed core learns it; the chained leaf does not.

A WRONG TEST, WORTH RECORDING. The first resilience check asserted that a dead
site's topic disappears from the survivors' listings, and failed all four
topologies. The implementation was right and the test was wrong: federation has
TWO clocks, and neither is the 6s registry staleness.

    fed_serve_until_us  = 30s    the entry stops being HANDED OUT to subscribers,
                                 "because pointing a subscriber at an unreachable
                                 host just makes it retry", and stops being relayed
    fed_forget_after_us = 300s   the entry is REMOVED from the directory

So a topic whose publisher died ten seconds ago is still listed, on purpose, and
judging resilience by the listing measures expiry rather than topology. Both
clocks were then confirmed against the registry's own answer to `sub`, which
distinguishes all three states where a listing cannot:

    t+  8s   listed=True    tcp://127.0.0.1:50838                 served
    t+ 41s   listed=True    error: topic fed/e/beacon expired     withheld
    t+311s   listed=False   error: topic fed/e/beacon not found   forgotten

The instrument mattered twice over. The first attempt asked whether `qnnt-cat`
printed "subscribed to ... @ tcp://...", which it prints only on a successful
ATTACH -- so against a dead publisher it prints nothing whether or not an endpoint
was handed out, and it reported a mismatch at t+8s that was an artifact of the
probe. Asking the registry directly is what separated the two.

--------------------------------------------------------------------------------
 18. When the registry holder dies: examples/registry/
--------------------------------------------------------------------------------

    python3 examples/registry/failover.py --runs 5

The directory is host-local and lives in ONE elected process. Every node loops on
binding the registry port; whoever gets it serves, and the rest stand by and
re-probe every registry_probe_interval_ms (2s). So the holder is a single point of
failure for a host -- the mechanism is there in registryRun(), but nothing measured
what it costs.

Three processes keep the roles apart so the answers are not confounded: A holds
the registry and publishes nothing, B publishes at 10 Hz, C subscribes before the
kill and counts across it. Then A is killed.

RESULT: the directory is unavailable for 0.2s, and delivery never pauses.

Getting there took two changes and one retracted conclusion.

    measured                          role taken   gap    outage
    as found                          1.8-2.0s     0.0s   2.0s
    + bind retry 2000ms -> 250ms      0.2s         1.8s   2.0s   (no better!)
    + warm standby directories        0.2s         0.0s   0.2s

The middle row is the interesting one. Shortening the bind retry made the role
change hands ten times faster and did NOT improve the outage at all, because both
paths are gated by the same thing: a new holder starts with an EMPTY directory and
can serve nothing until publishers re-register on their 2s refresh. Taking the
role sooner only moves the wait.

So the fix is the warm copy, and the two changes only pay off together -- fast
takeover is worth nothing without something to serve, and a warm copy is worth
little if taking the role is what costs the time.

HOW THE WARM COPY WORKS. A standby already wakes to re-contend for the port, so it
pulls the directory from the holder in the same loop and merges it. Pulled, not
pushed: no registration with the holder, no fan-out, no tracking which standbys
are alive, and no failure mode where a slow standby stalls the holder's publish
path. A missed pull corrects itself on the next one, and the copy being up to one
interval stale does not matter, because a standby's copy is only ever read at the
moment it takes the role.

It reuses federation's machinery rather than repeating it: `mirror` returns the
same `fed-entry` lines federation exchanges, and `applyMirrorEntries` merges them
through the same `applyRemoteEntry`. So a standby inherits the whole merge policy
for free -- version ordering, first-registration-wins, and the refusal to accept
an entry bearing its own NodeId, which is what stops a stale copy of a node's own
registration overwriting the live one it is still refreshing.

The two intervals are now separate constants, because they answer different
questions and cost different amounts:

    registry_bind_retry_ms   250   a socket, a failed bind, a close: nothing on
                                   the wire, so it can be fast
    registry_probe_interval_ms 2000  a round trip per publisher, and the unit
                                   stale_after_us is expressed in

A CONDITIONAL PULL, so a quiet host costs almost nothing. A standby quotes the
epoch it last mirrored and the holder answers in one line if nothing has changed:

    mirror                    -> mirror-state <holder-id> <epoch>, then the entries
    mirror <holder-id> <epoch> -> mirror-unchanged <holder-id> <epoch>   (51 bytes)
                              -> or the whole thing, if either differs

The epoch is a counter, not a digest, and that is deliberate: `version` on an entry
is set to `now_us` on EVERY refresh, so anything derived from entry contents
changes every probe interval per publisher and a "has it changed?" check built on
it would never once say no. The registry already computed the right signal --
`registerTopic` sets `changed` only when a topic appears, its endpoint moves, or it
goes away, precisely so federation is not woken by heartbeats -- so the epoch is
that existing signal, counted. No hashing, no collisions, and one line where the
notification already fired.

The holder's NodeId travels with it because the counter is per-process: a standby
holding epoch 42 from one holder is not current against a different holder that
reached 42 by another route, and answering "unchanged" there would leave it
mirroring a directory it never saw.

ONE SUBTLETY, and it is the kind that would have gone unnoticed for a long time.
Merging is what refreshes a mirrored entry's lease -- `entryIsServable` stops
serving anything this node has not heard about for 30s. A standby that only ever
received "unchanged" would therefore watch its warm copy quietly go cold, and then
on takeover refuse to serve topics that had been alive the whole time. So a full
pull is forced every `serve_until_us / 2`, and the cheap path covers the rest.
Verified by settling for 45s -- long past the lease -- before killing the holder:
resolvable again in 0.11s.

WHAT IT COSTS, derived from 94 bytes per entry measured on the wire, a 2s poll and
a forced full pull every 15s:

     4 nodes,  50 topics      6.9 -> 1.0 KiB/s per host
    10 nodes, 100 topics     41.3 -> 5.7 KiB/s per host
    50 nodes, 500 topics   1124.5 -> 151.0 KiB/s per host

about 7x less than pulling the whole directory every time. It remains
O(nodes x topics) on the full pulls, so a very large host still pays; sending only
the entries above the standby's epoch would remove that too, and needs a
per-entry "changed at" stamp to do it.

TWO OPT-OUTS, for hosts that should not carry this at all:

    QNNT_REGISTRY_ROLE=client    never be elected. The node publishes and
                                 subscribes normally but never contends for the
                                 port and never mirrors -- a warm copy exists only
                                 to make a takeover fast, and this node will not
                                 take over. For a sensor board or a tight
                                 container that should not be handed the whole
                                 host's directory.
    QNNT_REGISTRY_MIRROR=0       stay a candidate, but cold. Able to take the
                                 role, without the round trip every probe interval
                                 or the copy in memory -- which is exactly the
                                 behaviour before mirroring existed.

If every node on a host opts out of the role, the port stays vacant and there is
no registry. That is the configured outcome rather than a fault, and it is visible:
the declining node says so once, at startup.

    established delivery    never paused, in any run

Two things follow.

THE REGISTRY IS A CONTROL PLANE, exactly as federation is (section 17). An
established subscription is direct TCP between publisher and subscriber; the
registry is how the two were introduced, not how they talk. Killing it did not
drop a single message in any run.

RECOVERY IS TWO PHASES, and only the first is fixed. Taking the role costs up to
one probe interval, depending where the standby was in its cycle. Re-registration
costs a second one UNLESS the publisher itself takes over, in which case its topic
is already local to the directory it now serves and resolution is immediate --
usually. Five runs of six; the sixth still paid the second interval.

The timing is jittery enough that the harness takes `--runs N` and reports a
distribution rather than a verdict, which is not a stylistic choice: during
development this test produced a confident and WRONG answer twice from single
runs, first that the publisher case is always immediate, then -- over-correcting
on three samples that included the one outlier -- that it never is. Eight samples
say "usually, but not reliably".

FOUR INSTRUMENT BUGS, all mine, all in the probe rather than the library, and all
of the same shape -- an error path producing plausible data instead of an error:

  * `sub <topic>` sent with no trailing newline. The registry waits for the rest
    of the line and replies with its banner alone, which parses as an empty answer
    and is indistinguishable from "topic unknown".
  * "who holds the role" read by grepping a log for "role acquired", which reports
    EVER held, not currently. Read after teardown it showed two holders at once,
    because terminating one frees the port and the survivor grabs it on its way out.
  * (section 17) `qnnt-cat` used to detect whether an endpoint was handed out. It
    prints its line only on a successful ATTACH, so against a dead publisher it
    prints nothing either way.
  * (section 17) judging expiry by a topic listing, when listing and serving are
    two different clocks.

The registry answers all of these directly if asked properly. `sub <topic>`
distinguishes served / expired / not-found, and `list` shows refreshed age and
origin per entry.

 19. Testing the C++ side: examples/cpp_logic_test.cpp
--------------------------------------------------------------------------------

    zig build cpp-logic          # 80 checks, no Qt needed
    zig build test               # runs them too

The C++ half of this repository had no tests at all. Four viewers, and the one
crash that reached a user (camera-viewer at --scale below 4, fixed in cf1cd51)
lived there and survived several "verified end to end" runs.

The obstacle was structural rather than anything to do with willingness: the logic
sat inside .cpp files next to main() and a moc include, reachable only by building
a Qt executable. Anything testable only that way would in practice never be tested,
because the Qt targets are built only when -Dqt= is passed. So the logic came out
into headers that carry no Qt at all:

    examples/ugv/steering.hpp        differential steering, as arithmetic
    examples/dirigera/devices.hpp    what a device is FOR, and which get a row
    examples/dirigera/frames.hpp     the topic payload types
    examples/dirigera/frames.zig     their Zig counterparts, and the goldens

The viewers include the same headers, so the tests exercise the code that ships
rather than a copy of it.

WHAT IS CHECKED, and each of these is a bug that actually happened or nearly did:

  * The steering sign convention. A right turn drives the left track forward, so
    steerAxis is POSITIVE -- the quantity the pad indicator once derived a second
    time in QML and got backwards.
  * Normalising rather than clipping. Full forward plus half a turn wants 1.5 and
    0.5; clipping the first would leave the second alone and quietly straighten
    the curve. The test asserts the RATIO survives, since both approaches keep the
    values in range.
  * An unknown deviceType is Other, not whatever the first branch returns.
  * One physical sensor, one row: a VALLHORN's light-sensor half folds into its
    motion twin, but a light sensor with no twin keeps its own row.
  * Motion as an event: a repeated detection is not a new rising edge and must not
    restart the clock, or a sensor held in front of always looks like it just fired.

THE CROSS-LANGUAGE CHECK is the one nothing else makes. The station's structs and
the bridge's must agree field by field, and a mismatch is silent on both sides:
TLD ignores a key the receiving struct does not declare, and the TLD_DEFINE_MAP
macros leave a member the frame did not carry exactly as its constructor left it.
The result is plausible data -- a light that reports itself uncontrollable, a
sensor with no room -- not an error.

So the agreement is pinned to a golden frame, the same shape as lib/testdata/
interop.tld: examples/dirigera/testdata/*.tld holds bytes packed by Zig from
canonical values, a Zig test asserts they still pack to exactly those bytes, and
the C++ test asserts they unpack to the same values. Either side drifting fails.
The command direction is checked both ways, because a mismatch there is a click
that silently does nothing.

One thing that had to be designed for rather than assumed: EVERY plain bool in the
canonical frame is true. A `bool` default-constructs to false in C++, so a field
the station stopped declaring reads as false -- and a canonical value of false
would have been indistinguishable from a dropped field, letting the check pass
straight through the bug it exists to catch. False-ness is tested on the optional
bools instead, where absent and present-but-false are different things.

MUTATION-TESTED, because a passing test proves nothing about whether it would
catch the bug. Five deliberate breaks of the logic -- flip the steer sign, clip
instead of normalise, drop the unknown-type default, restart the motion clock on
every reading, invert the pairing rule -- all five caught. For the boundary, a
field renamed consistently across the C++ struct AND its macro AND the test
compiles cleanly and is caught by the golden with two failures; a rename that
misses the macro does not compile at all, which is a second layer rather than the
same one.

WHAT STILL HAS NO TESTS, stated plainly rather than left to be discovered: the Qt
classes themselves, every QML binding, and the frame decode and projection in
examples/zed/viewer.cpp and examples/lidar/viewer.cpp. The projection in
particular has had two bugs (a degenerate first-person eye, and a fov taken from
the wrong axis) and remains covered only by looking at it.

 20. Federation on real hosts: docker/
--------------------------------------------------------------------------------

    zig build -Dtarget=aarch64-linux-gnu     # or x86_64-linux-gnu
    bash docker/federation.sh

Six containers on one bridge network, each a host with its own address, running the
same four topologies as section 17 and then cutting a host off the network on
each. See docker/README.md for the operator's version of this; what follows is
what it added over the loopback harness.

WHY IT WAS WORTH BUILDING. Section 16 runs the topologies as ports on one machine,
which is faster and needs no Docker, and it stays the right check for most work.
Three things it cannot reach, all of which this does:

  * OBSERVED-ADDRESS SUBSTITUTION, which is the interesting one. No node here is
    told its own address -- none sets QNNT_ADVERTISE_ADDR -- so an entry travels
    with an empty host and the receiver fills in the address it was reached on.
    That is the whole NAT story in federation.zig, and on loopback it was
    untestable: every address is 127.0.0.1, so a wrong answer looks exactly like a
    right one. Here the script checks every learned endpoint against the peer's
    real container address, and a wrong answer is a wrong container.
  * THE DEFAULT PORTS. Registry 2222 and federation 2223 everywhere, because each
    host has an address of its own. The loopback harness must give every site
    different ports, which is not how anything is deployed.
  * A PARTITION. `docker network disconnect` removes a host the way a cable does:
    the process keeps running and keeps believing it is fine. Killing a process is
    a different failure, and it is the only one the loopback harness can produce.

Peers are named rather than numbered (QNNT_PEERS=alpha,charlie), so Docker's DNS
and the libc resolution path are exercised too -- an address literal skips both.

RESULT, 16 checks across the four topologies:

    all four converge              every linked host sees every linked topic
    learned endpoints              the peer's real address, never loopback
    a cut host stops being served  inside its 30s lease
    re-learned after healing       15-20s

A NOTE ON THE RECOVERY NUMBER, because the first version of this test got it
wrong. Recovery was asserted against a fixed 12s wait and failed on every
topology, which looked like federation not recovering from a partition at all. It
recovers in 15-20s; the test was impatient. It now polls and reports the time it
actually took, for the same reason the failover harness does: a fixed deadline on
a jittery quantity produces confident wrong answers.

LATENCY AND LOSS, with tc netem:

    bash docker/federation.sh netem

    a perfect network (the baseline)               2s
    100ms added to every host                      1s
    10% packet loss on every host                  9s
    one host at 2000ms: the four unaffected        8s
      and the slow host itself                     21s

Each number is how long a BRAND NEW topic published on one host takes to reach
every host being waited for -- a fresh name each time, since one already in the
directory would measure nothing.

Latency and loss turn out to be unremarkable. The exchange is TCP, so 10% loss
becomes retransmission rather than lost entries, and 100ms on every link changes
nothing measurable.

A SLOW PEER COSTS NOTHING MEASURABLE, and the claim that it did -- which stood
here for a day -- was an artefact of the instrument. Retracted.

The probe was `docker exec <host> qnnt-ls`, and qnnt-ls is itself a qnnt node: it
starts, contends for the registry port, becomes a standby and pulls a directory
mirror. That startup slows down when the host is busy, and a slow peer makes every
host busier. The probe was timing itself.

Timing the events INSIDE the system -- registration to applied -- shows no
difference at all:

    MESH, registration -> applied
      healthy      bravo=419ms charlie=419ms echo=418ms
      healthy      bravo=83ms  charlie=83ms  echo=83ms
      delta SLOW   bravo=329ms charlie=328ms echo=330ms
      delta SLOW   bravo=145ms charlie=308ms echo=310ms

WHAT THE CHASE DID FIND is a real defect, in relaying. Only two places called
notifyChange: a node's own outbound exchanges, and its own publishers. A host that
learned an entry by being PUSHED to updated its directory and told nobody, so it
did not relay onward until its 5s anti-entropy deadline. One hop hid it entirely --
in a star or a mesh every host hears the publisher directly -- but a chain paid it
per hop:

    RING, publisher -> third host
      before   5119ms   1252ms   5597ms      <- the 5s deadline, not a wake
      after     767ms   1050ms   1162ms

End to end the ring went from 2.7s to 0.7s, in line with the star and the mesh.
That 2.7s had been recorded in section 17 as the cost of multi-hop relay. It was
this, and it was fixable.

WHAT IT STILL DOES NOT COVER. Sustained behaviour -- these runs last minutes, so a
slow leak or an entry ageing out wrongly over hours would not show. And one bridge
with one MTU and no middlebox says nothing about a real WAN path, a NAT that
rewrites addresses, or a firewall that drops idle connections.


--------------------------------------------------------------------------------
 21. A CAN gateway mesh: examples/can/
--------------------------------------------------------------------------------

Several hosts, each with a local CAN interface, joined so that a frame put on one appears
on all the others -- and several such buses at once over the same mesh, never mixing.

    zig build can -Dtarget=aarch64-linux-gnu     # Linux only; see below
    docker/can.sh

    qnnt-can-gw --name alpha --bus powertrain=vcan0 --bus body=vcan1

Each gateway publishes what it reads from a local interface, and subscribes to the shape of
what every other gateway publishes:

    can/<bus>/<gateway>     frames <gateway> read from its local <bus>
    can/<bus>/*             what each gateway subscribes to

That second line is the whole example. A gateway is never told the names of its peers, is
never given a list to keep in step, and needs no restart when one appears: it subscribes to
a shape, and a gateway that joins later is found because its topic turns up in the
directory. Adding a fifth host is editing one host's QNNT_PEERS, not editing five gateways.
Section 13 is the call; this is what it is for.

THE BUS NAME IS LOGICAL, NOT AN INTERFACE NAME. The segment this host reaches on vcan0 may
be vcan1 on the next, and `--bus powertrain=vcan0` says which is which. Naming the wire
after one host's cabling is how two unrelated segments end up spliced together.

TWO BUSES ARE TWO NETWORKS. `--bus powertrain=vcan0 --bus body=vcan1` bridges both over one
mesh and one federation link, and nothing crosses between them, because a topic names its
bus. In docker/compose.can.yml one host deliberately bridges powertrain only: it is
federated with hosts carrying body traffic and must never see any of it. The separation is
the topic, not the network.

LOOPS ARE PREVENTED TWICE, and both are needed:

  * The handler skips its own topic. `can/<bus>/*` matches `can/<bus>/alpha`, because
    matching means matching -- the library does not special-case a subscriber's own topics,
    and the handler is given the topic name precisely so it can decide. Without this check
    a frame would be written straight back to the bus it came from, duplicating every local
    message.
  * SocketCAN does not loop a transmitted frame back to the socket that sent it. One socket
    per bus does both the reading and the writing, so a frame this gateway injects is never
    read by its own reader and never republished. Without this, a frame from alpha would be
    injected at bravo, read back by bravo, republished as bravo's, injected at alpha, and
    the mesh would saturate in under a second. The gateway sets CAN_RAW_RECV_OWN_MSGS to 0
    explicitly rather than relying on the default, because the whole design rests on it.

The consequence of the second rule is a constraint worth stating: ONE GATEWAY PER INTERFACE
PER HOST. Two gateways on one vcan would each read the other's injections.

What travels is not `struct can_frame`. That struct is a Linux ABI -- an identifier and
three flags sharing one word at bit positions the kernel chose -- and putting it on the
network would oblige every other consumer to know those positions. So the flags are named
fields and the identifier is already masked; see examples/can/frame.zig. Error frames are
published, so a monitor sees bus health, but never written to another segment: an error
frame describes a condition on the segment that produced it, and injecting it elsewhere
reports a fault on a bus that is healthy.

THE STATION: can-station
------------------------

    zig build can-station -Dqt=/Users/you/Qt/6.10.3/macos
    bash examples/can/demo.sh        # four gateways and two buses to look at
    ./zig-out/bin/can-station        # or against gateways of your own

`demo.sh` produces the mesh with examples/can/wire_check.py rather than with gateways on
vcan interfaces, so it needs no CAN support and runs anywhere Qt does. It publishes exactly
the topics and exactly the frames a gateway publishes, and the station cannot tell the
difference -- which is the point. Everything it starts is stopped when the window closes,
including if you interrupt it: four publishers left talking to nobody is not a good way to
end a demo. For the real thing, gateways on real interfaces, see docker/can.sh.

A Qt/QML view of the whole mesh, and a node on it. The fifth station in this repository and
the first that does not know what it is looking at when it starts: lidar-viewer is pointed
at a topic, ugv-pilot at a robot, dirigera-home at a bridge. This one subscribes to
`can/*/*` and finds out. Which buses exist, which gateways are on them, and which
identifiers those gateways carry are all read off the topic names, because a topic name is
all a gateway publishes about itself.

It is NOT Linux-only, unlike the gateway. It watches topics, and a topic does not care which
kernel produced it -- so it runs on a mac against gateways on any number of Linux hosts.

    left     the mesh: each bus, and under it every gateway publishing to that bus, with
             its own rate. A gateway that has stopped shows here and nowhere else.
    centre   the bus: one row per CAN identifier, in identifier order, with the latest
             payload, its rate, and which gateway last carried it.
    bottom   send: compose a frame -- classic or FD -- and put it on the bus, once or
             every N milliseconds.

The flag column reads E extended, R remote, F CAN FD, B bit rate switch, P error-passive
transmitter, ! error frame. F is not decoration: an eight-byte FD frame and an eight-byte
classic frame differ in nothing else a row shows, and they are different frames.

Three of its decisions are worth knowing.

  * THE SCREEN IS REFRESHED ON A TIMER, NOT ON A FRAME. A CAN bus at 500 kbit/s carries a
    few thousand frames a second and a mesh carries the sum of all of them. Touching a QML
    model per frame would spend the machine on layout and still show a blur. Frames update
    counters; the view is refreshed at 10 Hz.

    REFRESHED, not rebuilt. The first version handed QML a freshly built list every tick,
    which resets a ListView and destroys every delegate with it -- measured at twelve
    rebuilds a second per row. A click's press and its release then almost never landed on
    the same item, so the bus list could not be clicked at all. The lists are stable QObjects
    now: a tick updates their properties in place, and a list changes identity only when a
    bus or an identifier actually appears. Same measurement afterwards: 3 rather than 204.
  * A ROW PER IDENTIFIER, NOT A SCROLLING LOG. A bus repeats a handful of identifiers
    endlessly, so a scroll shows the fastest and hides the rest. Standard and extended
    identifiers with the same number stay on separate rows, and so do classic and FD ones,
    because each pair is two conversations to every controller on the bus.

    Ordered by identifier, not by rate. Rate ordering reads well in a screenshot and is
    unusable in motion: live rates cross constantly, so rows swap places while you are
    looking at them. cansniffer orders by identifier for the same reason -- the rate is a
    column you read, not a position you chase.
  * SENDING IS REAL. The station publishes on `can/<bus>/<its own name>` exactly as a
    gateway does, so every gateway on that bus writes the frame to its local interface. It
    is a participant, not an observer, which is why the payload box refuses a malformed
    value rather than padding it: "12 3" is a typo, and guessing whether it meant 0x03 or
    0x30 puts a frame nobody wrote onto real hardware.

    Ticking `every` sends it at a fixed period instead of once, which is what a bus
    actually carries -- almost every message on a vehicle bus is periodic, and a receiver
    under test is written against the pace, not against a single frame. The period is
    1-60000 ms -- 1 ms being roughly a full 500 kbit/s bus -- and a value outside that is
    REFUSED rather than clamped, since quietly substituting one reports a load the bus is
    not carrying. The sender uses a precise timer, but the achieved rate is the machine's
    to give: measured by an independent subscriber, 10 ms delivered 101 frames/s and 2 ms
    delivered 504, both exact, while 1 ms delivered about 894 rather than 1000. The row's
    own rate column is what actually went out, and at the shortest periods that is the
    number to believe. Everything is validated once when the
    repeat starts, so the timer does no parsing; editing a field while it runs restarts it
    on the new value, and a publish that fails stops it rather than retrying into a fault
    every period. Measured with an independent reader: 101 frames in 5 s at 50 ms.

Its own topic matches its own pattern, so the station appears in its own gateway list --
marked, because a reader who did not know that would think a gateway had duplicated.

Watching it needs no special tool either. The frames are TLD on ordinary topics:

    qnnt-ls --tree
    qnnt-cat 'can/powertrain/*'          # every host's view of one bus
    qnnt-cat 'can/*/*'                   # every bus, every host
    candump vcan0                        # and the ordinary CAN tool, locally

A KERNEL WITH CAN IS REQUIRED, and this is the part that trips people up. CAN is a kernel
subsystem: `vcan` needs CONFIG_CAN and CONFIG_CAN_VCAN. Any mainstream distribution kernel
has them as modules. DOCKER DESKTOP'S LINUXKIT KERNEL HAS NEITHER -- not as a module and
not built in -- so no amount of --privileged will create a vcan interface on a Mac or a
Windows box running Docker Desktop. Check in one line:

    docker run --rm --privileged --entrypoint bash debian:bookworm-slim \
      -c 'ip link add dev p type vcan && echo yes || echo no'

This is an upstream gap, not a setting. linuxkit/linuxkit#3486 has been proposing exactly
these options since March 2020 and is still open -- it stalled because the kernel build
checks that the config file does not change during the build, so the options could not
simply be appended. The workaround in that thread builds a CUSTOM LinuxKit image and boots
it with `linuxkit run qemu`, which is a VM of your own next to Docker Desktop rather than a
change to it: Docker Desktop ships its own signed VM and offers no way to substitute a
kernel. If the PR ever merges, this example needs no change -- the harness probes for vcan
and would simply stop skipping.

The way to run it on a Mac is a VM with an ordinary distribution kernel instead of
LinuxKit's. colima boots Ubuntu, where CAN is a loadable module, and everything under
docker/ runs there for exactly this reason -- one runtime has to be able to run all of it.
Setting it up is one command:

    brew install colima
    docker/colima.sh          # start the VM, load the CAN modules, select the context
    docker/can.sh             # 15 checks
    docker/colima.sh stop

Two things it hides for you. The Ubuntu CLOUD image ships a trimmed module set, so vcan is
missing until `linux-modules-extra` is installed -- `modprobe vcan` fails with "Module vcan
not found" on a fresh VM, which reads exactly like a kernel without CAN and is not. And the
module loads in the VM, never in a container: a container has no /lib/modules and cannot
modprobe anything, it can only `ip link add` against a subsystem the kernel already has.
Modules do not survive a VM restart either, so `docker/colima.sh` is run after every
`colima start`; that is all it does the second time.

`docker context use desktop-linux` goes back to Docker Desktop for everything except this
example. The two keep separate image stores, so rebuild after switching.

docker/can.sh detects this and says so rather than failing obscurely, then runs the half
that does not need a kernel:

    docker/can.sh            # the gateways, or the reason they cannot run here
    docker/can.sh wire       # the qnnt half only: topics, globs, federation
    docker/can.sh shell alpha

`wire` runs examples/can/wire_check.py in place of the gateways. It speaks exactly the same
topics and publishes exactly the same TLD frames, so it exercises the topic layout, the glob
subscription, the federated directory and the frame format -- everything except the socket.
It is also a cross-language check on that format: the frames are packed by Python against
the field names in frame.zig, so a rename on either side shows up as a gateway that receives
and silently discards. When the real harness fails and this one passes, the fault is in
SocketCAN or in the interfaces, not in the mesh.

WHAT THIS FOUND. Federation merged a peer's entries into the directory without moving
`directory_epoch`. Everything that polls for CHANGE rather than for content watches that
number -- a `subscribePattern` re-lists only when it moves, and a warm standby re-pulls its
mirror only when it moves -- so a topic reached through federation was a topic no glob
subscription on the receiving host would ever join. The gateways each saw only their own
traffic. It was invisible until now because nothing before this subscribed to a PATTERN
across a federation boundary: a named subscription resolves the topic directly and never
consults the epoch at all.

WHAT IS COVERED, and by what. Three layers, because they fail in different ways and only
the first runs without a Linux kernel:

  * `zig build test` -- the wire format, the topic layout, the flag decoding, and the rules
    about what may be written to a bus. Runs anywhere, mac included.
  * `docker/can.sh wire` -- the topics, the glob subscription, the federated directory and
    the frame format across five hosts. Needs Docker, not CAN.
  * `docker/can.sh` -- the SocketCAN calls themselves and the gateways end to end. Needs a
    kernel with vcan.

The middle layer is not a substitute for the third, and the difference is not academic: the
first version of this example passed every check above the socket while relaying eight bytes
of garbage in every frame. `read` returned a frame whose payload borrowed its own stack, so
it dangled the moment it returned. The identifier was right, the length was right, and the
payload was a leftover pointer -- the same eight bytes on every frame, on every host. Only
running it against a real interface showed it. examples/can/socketcan.zig now carries tests
for the round trip, for 29-bit identifiers, and for the loopback rule the loop prevention
depends on; they are built by `zig build can` and run by the harness, since they need a bus
to talk to.

The struct layouts are checked separately, at compile time: every size and offset is
asserted against the numbers <linux/can.h> produces, verified on both aarch64 and x86_64.

The station adds a fourth layer, `zig build cpp-logic`, which is Qt-free on purpose: topic
parsing, identifier and payload formatting, the hex parser behind the send box and the rate
estimator are ordinary C++ and are tested as such, and the wire format is pinned to
testdata/can_frame.tld -- bytes packed by Zig, unpacked by the C++ struct, so a field
renamed on either side fails a test instead of drawing a frame with identifier 0.

That last layer found a hole in the C API rather than in itself. An empty payload -- a
legal CAN frame with DLC 0, and every remote request -- could not be encoded from C++:
`std::vector<T>::data()` on an empty vector may return null, and the TLD writers rejected a
null pointer outright instead of reading (null, 0) as the empty buffer it means in C. It
threw, and in the station an uncaught exception took the window down. The three writers now
accept it.

CLASSIC CAN AND CAN FD, on the same bus and the same socket. The gateway sets
CAN_RAW_FD_FRAMES, which makes the kernel deliver both formats -- and the SIZE OF THE READ
is the only thing that distinguishes them, because an eight-byte FD frame and an eight-byte
classic frame are otherwise identical and are different frames to a controller. 16 bytes is
classic, 72 is FD. The same rule runs backwards on transmit: the size written is what tells
the kernel which to send.

So `fd` is carried on the wire as a field of its own rather than inferred from the length,
alongside `brs` (the data phase ran at the faster bitrate) and `esi` (the transmitter was
error-passive). Both belong to the FD data phase, and a classic frame carrying either is
refused: it describes something that will not happen. CAN FD has no remote frames, so `fd`
and `rtr` together are refused for the same reason.

CAN FD lengths are not arbitrary. The four-bit code has sixteen values, which mean 0-8, 12,
16, 20, 24, 32, 48 and 64 -- there is nothing between 8 and 12, or 24 and 32. A frame
claiming 13 bytes is malformed, not a short 16-byte frame, and is refused rather than padded
up: three bytes nobody wrote would go onto the bus.

An FD frame will not leave an interface whose MTU is still 16 -- the write fails with
EMSGSIZE. `ip link set vcan0 mtu 72` is what the link needs, and
examples/can/start-gateway.sh does it. A vcan at MTU 72 carries classic frames unchanged, so
it costs nothing.

 22. Stopping one topic: removePublisher and removeSubscriber
--------------------------------------------------------------------------------

Until now a publisher or a subscriber lived until the whole node did. These stop one topic
and leave the rest of the node running.

    Zig     Qnnt.removePublisher("bus/one")
            Qnnt.removeSubscriber("bus/one")

    C       qnnt_remove_publisher("bus/one", 7);
            qnnt_remove_subscriber("bus/one", 7);

    C++     node->removePublisher("bus/one");
            node->removeSubscriber("bus/one");

    Python  node.remove_publisher("bus/one")
            node.remove_subscriber("bus/one")

Both answer "was there anything to remove" -- false/QNNT_FAILED when that topic was not
running here. That makes them safe to call speculatively rather than tracking what you
started.

WHAT REMOVAL ACTUALLY DOES

A publisher is three threads, not one: the accept loop holding the listening socket, the
loop that refreshes the registry every couple of seconds, and (if you gave it a period) the
scheduler calling your source. `removePublisher` stops all three, then drops the
registration with the registry's `unpub` verb and closes the connections its subscribers
were reading from.

The order matters and is not the obvious one. The refresh loop is joined BEFORE the `unpub`
goes out -- reverse it and the loop re-registers the topic a moment later, leaving a
directory entry pointing at a socket nobody is listening on.

A subscriber is one thread parked in a read. `removeSubscriber` breaks that read and joins
it, and takes EVERY subscription on the name: subscribe to the same topic twice and one
call removes both.

THE GUARANTEE, AND THE ONE TRAP

Both calls JOIN. When they return, no thread is left reading, writing or calling back on
that topic, so whatever your callback's user pointer pointed at is yours to free.

That guarantee is exactly what makes the trap: calling either from the topic's own callback
would have the thread wait for itself. That is refused -- false, and a line on stderr --
rather than deadlocking. If you need a topic to stop itself, set a flag and remove it from
whichever thread drives your program.

    // WRONG -- this is the callback's own thread
    void on_message(const char *topic, size_t n, const uint8_t *d, size_t len, void *u) {
        if (looks_done(d, len)) qnnt_remove_subscriber(topic, n);  // returns QNNT_FAILED
    }

    // Right: the callback raises a flag, the main loop acts on it.
    if (atomic_load(&done)) qnnt_remove_subscriber("bus/one", 7);

GLOBS

A topic joined by `subscribePattern` can be removed like any other, and it stays removed:
the pattern keeps a record of every topic it has ever joined, so its next rescan passes
over that name instead of resubscribing. Removing the pattern itself is not a thing --
there is no handle for it. To stop a whole glob, stop the node.

WHAT IT IS NOT

Not a pause. There is no retention in qnnt, so a removed-and-recreated publisher is a new
publisher: subscribers see a disconnect and reconnect, and anything published in between
reached nobody. That is the same thing they would have seen had the process restarted.

 23. Request/reply: procedures
--------------------------------------------------------------------------------

Everything else in qnnt is one-way. A procedure is the other shape: one request, one reply,
addressed to a name.

SERVING

    Zig     Qnnt.addResponder("arm/home", handler, ctx)
            Qnnt.removeResponder("arm/home")

    C       qnnt_add_responder("arm/home", 8, handler, NULL);
            qnnt_remove_responder("arm/home", 8);

    C++     node->addResponder("arm/home", [](auto name, auto req) -> std::optional<QByteArray> {
                return QByteArray("done");
            });

    Python  node.add_responder("arm/home", lambda name, req: b"done")

A handler returns the reply, or refuses: `null` in Zig and C, `std::nullopt` in C++, `None`
in Python. Refusing is NOT the same as replying with nothing -- the caller can tell them
apart, which is what the status byte on the wire is for.

Requests are served ONE AT A TIME, so a handler that touches shared state needs no lock
against itself. It runs on the responder's own thread, not yours.

The bytes a handler returns are written to the socket AFTER it returns, so they must
outlive the call -- a literal, a global, or heap you keep alive, never a buffer on the
handler's own frame. Same rule as a publisher's source callback.

CALLING, BLOCKING

    Zig     var out: [4096]u8 = undefined;
            var len: usize = 0;
            const status = Qnnt.request("arm/home", "now", 2000, &out, &len);

    C       qnnt_rpc_status rc = qnnt_request("arm/home", 8, "now", 3, 2000,
                                              out, sizeof out, &len);

    C++     QByteArray reply = node->request("arm/home", "now", 2000);

    Python  reply = node.request("arm/home", b"now", timeout=2.0)

The status says what happened, and the distinctions are the point: `no_procedure` (nothing
of that name, or it is a topic), `unreachable` (resolved, host did not answer),
`timed_out`, `refused` (the handler declined), `too_large`.

`no_procedure` comes back IMMEDIATELY rather than after the timeout: the registry either
knows the name or does not, so calling something that is not there costs a round trip to
loopback, not five seconds.

CALLING, NON-BLOCKING

This is the part the old Qt interface never had. `request` blocks, which is fine in a
script and wrong in a GUI or a control loop: a 5 second timeout against an unreachable host
freezes the caller for 5 seconds.

    Zig     const id = Qnnt.requestBegin("arm/home", "now", 2000);   // returns at once
            var out: [8]Qnnt.QueuedReply = undefined;
            for (Qnnt.pollReplies(&out, 100)) |r| { ... r.id, r.status, r.data ... }

    C       uint64_t id = qnnt_request_begin("arm/home", 8, "now", 3, 2000);
            qnnt_poll_replies(replies, 8, 100, &count);

    C++     quint64 id = node->requestBegin("arm/home", "now", 2000);
            // connect(node, &QnntNode::replyAvailable, ...) -- fires on the Qt thread

    Python  ticket = node.request_begin("arm/home", b"now", timeout=2.0)
            for reply in node.poll_replies(timeout=0.1): ...

`requestBegin` returns a ticket, 0 if it could not be started at all. Replies are DRAINED,
not delivered by callback, for the same reason `subscribeQueue` exists: a completion
callback would fire on a library thread, and entering a managed runtime from a thread it
has never seen means taking the GIL and having nowhere to put an exception. Drain replies
and messages from the same loop.

The ticket is how a reply is matched to its call. Several can be in flight at once, they
complete in whatever order they finish, and each carries the procedure that answered so one
drain loop can serve many call sites. The Qt binding does the draining for you and emits
replyAvailable() on the object's thread.

There is a bound -- 256 in flight -- because each one holds a thread. Past it,
`requestBegin` returns 0 rather than growing without limit.

WHAT IT COSTS, AND WHEN NOT TO USE IT

One TCP connection per call. That is deliberate: no correlation ids, no multiplexing, no
head-of-line blocking between callers, and a dead peer is a failed connect rather than a
request waiting for a reply that is never coming.

It also means a request is a CONTROL-PLANE operation. For anything at streaming rates,
publish: a topic amortises one connection over every message that follows, and a procedure
pays for a new one each time.

NAMES

Procedures and topics share one namespace and one directory, so a procedure federates
across hosts and expires exactly as a topic does, and `QNNT_PUBLISHER_PORTS` covers a
responder's listener like any other.

Sharing the namespace means they can collide, so the directory entry records which it is
and the two resolve separately: requesting a topic is `no_procedure`, and subscribing to a
procedure is an error rather than a connection that waits forever for a stream. That
deadlock is what the entry kind exists to prevent -- of all the ways a name collision could
be reported, two ends blocked on each other is the worst.

Older peers federate fine: the kind is a field appended to `fed-entry`, and a build that
predates it reads the six fields it knows and ignores the rest.
