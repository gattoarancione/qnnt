qnnt transport benchmark -- real hosts, real links
==================================================

Two targets, measured 2026-09-01, each against the same commit built with
-Doptimize=ReleaseFast:

  A   x86_64 desktop linux, reached from the development mac over Wi-Fi + 100 Mb ethernet
  B   NXP i.MX gateway, aarch64 Cortex-A53 x4, kernel 6.6.52 SMP PREEMPT ("semi-realtime"),
      measured twice: over Wi-Fi (B.1-B.5) and over gigabit wired (B.6)

Loopback figures are included for both, not as the headline but because without them there
is no way to tell whether a LAN figure is reporting the library or the network. On both
targets the answer over the LAN was the network, every time.

Short version:

  * qnnt reaches the link's capacity on every path measured -- 94-99% of raw TCP on target
    A, within the link's own run-to-run variance on target B over Wi-Fi, and exactly line
    rate (117.67 of 117.60 MB/s) on target B over gigabit wired, in both directions, with
    a Cortex-A53 on one end.
  * on that gigabit path, at 64 B frames, the transport finally becomes the bottleneck
    instead of the network -- and the board's send path turns out to cost 3.1x its receive
    path, because publishing writes once per frame while receiving amortises one read
    across many. Section B.6; it is the most informative measurement in the file.
  * on-board and uncontended, the round trip is bounded under 1.1 ms across 18,000 trips
    for 9% of one of four cores. Under CPU contention that bound needs SCHED_FIFO, which
    QNNT_RT_PRIORITY now provides: p99 goes from ~5 ms back to 128 us. Sections B.5, B.7.
  * the whole of target B re-run with that configuration is in B.8, including the two places
    it does not help: throughput is unchanged, and on an unpaced publisher a real-time
    priority costs 10% and adds 50 ms stalls via the kernel's RT throttle.
  * its round trip bottoms out below ICMP's minimum on both paths, so the transport adds
    nothing measurable to a network round trip.
  * on target B, entirely on-board, the round trip is bounded under 1.1 ms across 18,000
    consecutive trips at ~900 Hz, for 9% of one of four cores. That bound survives only
    while the CPU is uncontended: saturate all four cores and p99 goes from 768 us to
    ~5 ms. See section B.5 -- it is the one result with an action attached.
  * not one gap, and not one corrupt payload, in any run on either target.

TARGET A -- x86_64 desktop linux over Wi-Fi and 100 Mb ethernet
===============================================================

A.1  the path
----------------------------

  mac      192.168.16.204, Wi-Fi (en0), 802.11ax on channel 11 -- 2.4 GHz, 20 MHz wide
           signal -44 dBm (strong), PHY transmit rate 229 Mb/s
  linux    192.168.16.211 (eth0), 100 Mb/s full duplex, MTU 1500, x86_64
           the same host also has wlan0 on .210; eth0 carries this traffic

  ICMP round trip, mac -> linux, 30 packets:  min 3.24  avg 14.35  max 55.85 ms, 0% loss

The path is Wi-Fi to an access point, then wired to the linux box. There is no packet loss
on it, but the delay varies by a factor of twenty, which is 2.4 GHz airtime contention and
radio power save rather than anything qnnt does.

  raw TCP, single stream, 20 s, measured with the sink counting bytes:

      mac   -> linux     0.361 MB/s     (2.9 Mb/s)
      linux -> mac       1.157 MB/s     (9.3 Mb/s)

Both far below the 100 Mb/s wire and the 229 Mb/s radio: the mac's Wi-Fi uplink is the
limit, and it is asymmetric by 3.2x. This is the number every LAN figure below is compared
against, because it is what the path can carry at all.


A.2  the clocks disagree, which decides how latency is measured
------------------------------------------------------------

  clock offset, linux minus mac:   +86.396 ms      (best of 200 probes, best RTT 2.774 ms)

That matters more than it sounds. node-4 measures one-way latency by subtracting the
timestamp the publisher wrote from its own clock, which is exact on one host and useless
across two: 86 ms of offset against a few ms of real delay. In the linux -> mac direction
the subtraction even goes negative and clamps to zero.

So the latency figures here come from node-6 and node-5 instead. node-6 publishes a frame
stamped with its own clock, node-5 echoes it back unchanged, and node-6 subtracts using the
same clock that issued the stamp. No synchronisation is needed, or even a correct clock.
The result is a round trip rather than one way, which is the honest thing to report on a
link whose two directions differ by 3.2x anyway.


A.3  loopback ceiling -- the library with no network in the way
------------------------------------------------------------

linux box, node-3 -> node-4 on 127.0.0.1, publisher unpaced, ReleaseFast:

  payload    frame     frames/s     wire         payload      decode      gaps
  64 B       88 B      ~700,000     64.6 MB/s    45.0 MB/s    119 ns      0
  1 KiB      1050 B    ~527,000     562.7 MB/s   546.6 MB/s   126 ns      0
  64 KiB     65564 B   ~21,300      1426 MB/s    1425 MB/s     75 ns      0

Zero gaps and zero payload mismatches throughout; the payload is a 0..255 pattern checked
byte for byte, so a framing slip would show up as corruption rather than being missed.

Decode cost is flat in payload size -- 75 to 126 ns per frame whether the frame is 88 bytes
or 64 KiB -- because decoding walks fields, not bytes. The 64 KiB frame decodes *faster*
per frame than the 88 B one: same field count, and the cost is dominated by per-frame work.


A.4  over the LAN, linux publishing, mac subscribing
-------------------------------------------------

Publisher unpaced, so the link saturates and these are ceiling measurements. Compare the
wire column against the 1.157 MB/s raw TCP figure from section 1.

  payload    frame     frames/s   wire         payload goodput   framing   gaps
  64 B       88 B      ~12,700    1.16 MB/s    0.83 MB/s         72.7%     0
  1 KiB      1050 B    ~1,100     1.18 MB/s    1.15 MB/s         97.5%     0
  64 KiB     65564 B   ~18        1.18 MB/s    1.17 MB/s         99.96%    0

Wire throughput is the same at all three frame sizes and equal to raw TCP within the
variance of the radio -- the best 1 KiB window came out slightly above the raw figure taken
minutes earlier, which is Wi-Fi drifting, not qnnt beating TCP. The transport reaches the
link's limit regardless of frame size.

What frame size does change is goodput, and only through fixed framing overhead: 24 bytes
at 64 B payload, 26 at 1 KiB, 28 at 64 KiB. At 64 B payload more than a quarter of the wire
is envelope; at 1 KiB it is 2.5%; at 64 KiB it is not measurable. If a workload sends small
messages over a slow link, batching them into one frame is the only lever that matters.

Reverse direction, 1 KiB, against the 0.361 MB/s ceiling that way:

      mac -> linux       0.341 - 0.355 MB/s wire      94 - 98% of raw TCP,  0 gaps

Not one gap or corrupt payload was seen in any run, in either direction, at any frame size.


A.5  round trip latency, measured on one clock
--------------------------------------------

node-6 <-> node-5, 1 KiB frames at 20 Hz. That is 20 KB/s, under 2% of the link, so this
measures the path rather than the queue it builds when saturated.

  mac loopback (same host, for reference):
      min 83 us    p50 192 us    p90 256 us    p99 320 us    max 874 us

  mac <-> linux over the LAN, ten consecutive 5 s windows:
      min 2.66 - 4.02 ms
      p50 4.29 - 13.6 ms
      p90 23.0 - 79.8 ms
      p99 37.2 - 233 ms
      max 41.5 - 285 ms
      lost 0

The best round trip, 2.66 ms, is below ICMP's own minimum on the same path (3.09 ms
measured separately), so a full publish-subscribe round trip through two registries, two
TCP connections, an encode, two decodes and a re-publish costs less than the noise floor of
the network. The library's contribution is the loopback line: about 0.2 ms.

Everything above that is the radio. p90 to p99 spanning 23 to 233 ms with no packet loss is
2.4 GHz airtime contention, and it is the same shape ping shows (3 to 56 ms). Any latency
budget on a Wi-Fi LAN has to be written around this, not around the transport.

Under saturation the picture is different and worth stating plainly: with an unpaced
publisher, one-way delay grows to 145 ms at 64 B frames, ~550 ms at 1 KiB and ~950 ms at
64 KiB. That is queueing in the sender's socket buffer -- bufferbloat -- not transport cost.
A publisher that must bound latency has to pace itself below the link rate; qnnt will
happily fill the pipe if asked to.



TARGET B -- NXP i.MX gateway, aarch64 Cortex-A53, semi-realtime kernel
======================================================================

B.1  the target and the path
----------------------------

  board    NXP i.MX, "NXP i.MX Release Distro" (Yocto scarthgap, fsl-imx-xwayland)
           kernel 6.6.52 SMP PREEMPT, aarch64 Cortex-A53 (part 0xd03) x4, glibc 2.39
           1.8 GB RAM, 942 MB tmpfs on /tmp, hostname gw-lastMed-bench
           br0 192.168.3.1/24 bridging end0 (1 Gb/s) and end1; a cellular WWAN interface
           alongside it, not on this path

  mac      192.168.3.37 on Wi-Fi, associated to an access point bridged into br0

Note "SMP PREEMPT", not PREEMPT_RT: this is the low-latency preemption model, and there is
no /sys/kernel/realtime. It shortens preemption latency without giving any thread a
priority guarantee, which is exactly what section B.5 runs into.

The board has no zig, so everything was cross-compiled on the mac for its precise runtime
and CPU and copied over:

    zig build -Doptimize=ReleaseFast -Dtarget=aarch64-linux-gnu.2.39 -Dcpu=cortex_a53

  ICMP mac <-> board, 30 packets:   min 4.46  avg 11.78  max 26.54 ms, 0% loss
  ICMP again, later, 15 packets:    min 4.18  avg  7.48  max 19.02 ms, 0% loss

  raw TCP, single stream, 20 s:     mac -> board   9.26 MB/s
                                    board -> mac   9.65 MB/s

  clock offset, board minus mac:    +75.588 ms   (best of 200 probes, best RTT 3.97 ms)

Symmetric and about 26x target A's path, but still Wi-Fi on the mac's side: three
consecutive 12 s raw-TCP runs board -> mac gave 6.97, 7.93 and 9.09 MB/s. The link varies by
30% between measurements taken a minute apart, which sets the resolution of anything
measured across it. And the 75 ms clock offset is the same story as target A -- one-way
cross-host latency is not measurable, so latency here is again a round trip on one clock.


B.2  loopback ceiling -- the library on a Cortex-A53
---------------------------------------------------

node-3 -> node-4 on 127.0.0.1, publisher unpaced:

  payload    frame     frames/s     wire         payload      decode      gaps
  64 B       88 B      253,500      23.1 MB/s    16.2 MB/s    429 ns      0
  1 KiB      1050 B    158,900      167.4 MB/s   162.8 MB/s   435 ns      0
  64 KiB     65564 B   3,523        231.0 MB/s   230.9 MB/s   434 ns      0

Against target A's x86_64 box, same code and build flags:

                      x86_64          A53           ratio
  64 B frames         700,000/s       253,500/s     2.8x
  1 KiB frames        527,000/s       158,900/s     3.3x
  64 KiB throughput   1426 MB/s       231 MB/s      6.2x
  decode per frame    75-126 ns       429-435 ns    3.5-5.8x

Decode cost is flat in payload size here too -- 429 to 435 ns whether the frame is 88 bytes
or 64 KiB -- which is the property TLD framing exists for: decoding walks fields, not bytes.
The A53 is 3.5x slower per frame but the shape is identical.

The 6.2x gap at 64 KiB, wider than the 3.3x at 1 KiB, is memory bandwidth rather than
framing: at that size the work is moving 64 KiB through a loopback socket, and that is what
a 4-core A53 does 6x slower than a desktop x86.


B.3  on-board round trip -- the number this target is for
--------------------------------------------------------

node-6 <-> node-5 on the board, over loopback. No network, no second clock, no Wi-Fi:

  20 Hz, 1 KiB payload:
      min 148-461 us   p50 832 us   p90 832 us   p99 896 us   max 852-888 us

  1 kHz requested (912 Hz achieved), 256 B payload, one 20 s window of 18,248 trips:
      min 83 us        p50 448 us   p90 768 us   p99 768 us   max 1077 us

      cpu: node-6 5.0% and node-5 4.0% of one core, on a 4-core board

Zero lost, zero corrupt, in every window.

Two things worth reading twice. The tail is tight: p99 768 us and a worst case of 1.08 ms
across 18,000 consecutive round trips, each one a full publish, TCP hop, decode, republish,
TCP hop and decode through two registries. And the whole loop costs 9% of one of four
cores at ~900 Hz, so a control loop at this rate leaves the board essentially idle.

The mean is *lower* at 1 kHz (410 us) than at 20 Hz (745 us), and the minimum is half.
That is the sleep-wake path, not the transport: at 20 Hz each round trip pays for waking a
descheduled thread with cold caches, and at 1 kHz the path stays hot. qnnt is faster when
it is busy, which is worth knowing if you are sizing a slow control loop by measuring a
fast one, or the reverse.


B.4  across the LAN, board publishing, mac subscribing
-----------------------------------------------------

Publisher unpaced, so these saturate the link:

  payload    frames/s      wire              gaps    badpay
  1 KiB      6,166-7,888   6.49-8.31 MB/s    0       0
  64 KiB     96-128        6.30-8.41 MB/s    0       0

  raw TCP measured immediately afterwards, three runs:  6.97, 7.93, 9.09 MB/s

qnnt's range and raw TCP's range are the same range. Quoting a percentage would be
false precision: the Wi-Fi link varies more between consecutive 12 s runs than qnnt differs
from raw TCP, so the honest statement is that the transport reaches the link's capacity and
the link is what moves.

  round trip, mac <-> board, 1 KiB at 20 Hz (~2% of the link), nine 5 s windows:
      min 3.15 - 4.04 ms
      p50 7.23 - 10.88 ms
      p90 21.1 - 45.6 ms
      p99 40.9 - 210.5 ms
      max 46.4 - 264.6 ms
      lost 0 (two windows showed 1-2 frames still in flight at the boundary)

The best round trip, 3.15 ms, is again below ICMP's own minimum on the same path (4.18 ms
measured minutes earlier). Everything above it is the radio: compare the on-board figures
in B.3, where the same code on the same board answers in 768 us at p99. Crossing Wi-Fi
costs four to three-hundred times the transport itself.


B.5  the bound does not survive CPU contention
----------------------------------------------

Same on-board 1 kHz / 256 B round trip, with four shell spinners saturating all four cores:

                       idle              all 4 cores busy
      min              83-106 us         75-80 us
      p50              448 us            128 us
      p90              768 us            128 us
      p99              768 us            3,648-5,376 us
      max              785-1,077 us      6,312-47,132 us
      lost             0                 0

Nothing is lost, and the median actually improves by 3.5x -- with the cores pinned busy
there is no idle state to come out of and no frequency ramp, so the fast path gets faster.
But the tail collapses: p99 rises about 7x and the worst case about 45x, to 47 ms.

This is the SMP PREEMPT kernel behaving exactly as documented. Preemption latency is low,
but qnnt's threads run at default priority under SCHED_OTHER, so under contention they wait
their turn like anything else. Low preemption latency is not a scheduling guarantee.

This is what QNNT_RT_PRIORITY was added for -- see B.7, which repeats the experiment with
the worker threads on SCHED_FIFO and gets the bound back.

B.6  the same board on gigabit wired -- where the transport becomes the limit
----------------------------------------------------------------------------

Everything above for target B crossed Wi-Fi on the mac's side. Repeated with the mac moved
to wired gigabit (en7, 1000baseT full duplex, 192.168.3.44), talking to the same board over
the same bridge. This is the first path measured here that is fast enough for qnnt to be
the bottleneck rather than the network, so it is the most informative section in the file.

  ICMP, 30 packets:      min 1.816  avg 2.031  max 2.218 ms, stddev 0.069, 0% loss
  raw TCP, 3 x 12 s:     mac -> board   117.62, 117.61, 117.60 MB/s
                         board -> mac   117.30, 117.54, 117.57 MB/s

Line rate, symmetric, and stable to within 0.02 MB/s between runs -- so unlike the Wi-Fi
sections, a percentage here means something.

  clock offset, board minus mac:  +126.549 ms   (best RTT 1.073 ms)

It was +75.588 ms forty minutes earlier. The board's clock is drifting about 50 ms per
hour, which is what an embedded target with no time sync does, and is another reason the
latency figures here are round trips on one clock rather than one-way on two.

throughput, publisher unpaced, both directions:

                        board -> mac                      mac -> board
  payload   frames/s    wire        of link   frames/s    wire        of link
  64 B      270,000     24.9 MB/s   21%       845,800     77.8 MB/s   66%
  1 KiB     111,750     117.67 MB/s 100%      111,650     117.67 MB/s 100%
  64 KiB    1,795       117.68 MB/s 100%      1,795       117.67 MB/s 100%

  gaps 0 and badpay 0 in every run; board-side decode 426-435 ns/frame throughout

At 1 KiB and above qnnt saturates gigabit exactly: 117.67 MB/s against a 117.60 MB/s raw
TCP measurement, in both directions, with the A53 on one end. Frame size is irrelevant once
frames are large enough that per-frame cost stops mattering.

At 64 B frames it is not the link any more, and the two directions differ by 3.1x:

  * the board *sends* 270,000 frames/s (24.9 MB/s, 21% of the link)
  * the board *receives and decodes* 845,800 frames/s (77.8 MB/s, 66% of the link)

Receiving is three times cheaper than sending on the same CPU. The receive path reads
whatever the kernel has buffered and decodes many frames per read, so its syscall cost
amortises across frames; the publish path writes once per frame per subscriber, so it pays
a syscall per message and that is what caps it. Decode is not the constraint -- 426 ns per
frame is 2.3 M frames/s, well above what either direction reached.

The practical consequence: a publisher of small messages on this class of CPU is
syscall-bound at a few hundred thousand messages per second, and the fix is batching
several logical messages into one frame rather than anything to do with the codec. At 1 KiB
the same publisher reaches line rate, so the ceiling only bites below roughly 300 bytes.

round trip, node-6 on the mac and node-5 on the board:

                    20 Hz, 1 KiB          ~800 Hz, 256 B
      min           877 - 1,439 us        288 - 342 us
      p50           2,240 - 2,304 us      2,816 - 3,072 us
      p90           2,368 - 2,432 us      3,584 - 3,648 us
      p99           2,432 - 2,560 us      3,904 - 3,968 us
      max           2,423 - 3,048 us      4,154 - 5,050 us
      lost          0                     2 (in flight at the window boundary)

At 20 Hz the median round trip is 2.24 ms against an ICMP average of 2.03 ms on the same
path: the entire qnnt round trip -- two registries, two TCP hops, an encode, two decodes
and a re-publish -- costs about 210 us more than ping. The minimum, 877 us, is below ICMP's
own minimum.

Unlike the on-board case in B.3, here the faster rate is *slower*: p50 rises from 2.24 to
3.0 ms at 800 Hz. On loopback a hot path won; across the wire round trips start overlapping
and each one queues behind the ones before it, since node-5 decodes and republishes on a
single subscriber thread. The minimum still drops to 288 us, three times lower than at
20 Hz, so the fast path does get faster -- it just is not what the median sees.

against the same board over Wi-Fi (sections B.1-B.4):

                        Wi-Fi              wired            improvement
  throughput            6.5-8.4 MB/s       117.67 MB/s      14-18x
  round trip p50        7.2-10.9 ms        2.24 ms          3-5x
  round trip p99        40.9-210.5 ms      2.43-2.56 ms     17-82x

The tail is the headline. Wi-Fi's p99 varied by a factor of five between windows and reached
210 ms; wired, p99 sits in a 130 us band across every window measured. Nothing about qnnt
changed between those two rows.

One aside, observed by accident. Restarting node-6 while node-5 kept running reproduced the
publisher-restart path on a third platform: the new process gets a new NodeId, the board
held the old entry under first-wins, and node-5 stayed pointed at the dead endpoint until
the stale entry aged out. Recovery took longer than the 32 s test window, consistent with
the ~30-40 s measured on target A. Restarting both sides, or waiting, clears it.


B.7  the same contention, with a real-time configuration
--------------------------------------------------------

B.5 measured the tail collapsing under CPU contention because qnnt's threads ran at default
priority. Two settings address it, and they are separate concerns:

  QNNT_RT_PRIORITY=40     SCHED_FIFO for every worker thread, so nothing at default
                          priority can preempt them
  QNNT_LOCK_MEMORY=1      mlockall, so a page fault cannot stall a thread that scheduling
                          alone has made unpreemptable

(qnnt_set_realtime_priority / qnnt_set_lock_memory in C, Qnnt.setRealtimePriority /
Qnnt.setLockMemory in Zig, realtime_priority= / lock_memory= in python.)

Same board, same 1 kHz / 256 B on-board round trip, priority 40:

                    default         SCHED_FIFO 40   FIFO 40 + mlockall
                    4 cores busy    4 cores busy    4 cores busy
      min           75-80 us        78 us           78-82 us
      mean          219-461 us      85-87 us        85-87 us
      p50           128 us          128 us          128 us
      p90           128 us          128 us          128 us
      p99           3,648-5,376 us  128 us          128 us
      max           6,312-47,132 us 155-445 us      117-170 us
      lost          0               0               0

and idle, for reference, where there is nothing to preempt and little to fault:

                    default         SCHED_FIFO 40   FIFO 40 + mlockall
      p50 / p99     448 / 768 us    448 / 768 us    448 / 448-768 us
      max           785-1,077 us    769-951 us      694-1,013 us

SCHED_FIFO does the heavy lifting: under contention p99 goes from about 5 ms to 128 us and
the worst case from 47 ms to 445 us, a factor of 40 at p99 and 100 at the tail. The bound is
not merely restored, it is better than the idle case -- with four cores pinned busy there is
no idle state to leave and no frequency ramp to wait for, and a real-time thread preempts
the spinners immediately.

mlockall then takes the residual tail: the worst case drops again from 445 us to 170 us
without moving p50 or p99, which is exactly the signature of removing occasional page
faults rather than a systematic cost. Neither setting changes the idle columns, as expected.

So the full configuration on this board, with all four cores contended, is p99 128 us and a
worst case of 170 us -- against 5 ms and 47 ms unconfigured.

Verified that the policy is actually in force rather than merely requested:

    PID     TID CLS RTPRIO COMMAND
   2546    2546  TS      - qnnt-node-0     <- the caller's own thread, deliberately untouched
   2546    2548  FF     40 qnnt-node-0
   2546    2549  FF     40 qnnt-node-0     <- seven workers, all FF at 40
   ...

One measurement worth repeating, because it decided how locking is implemented. qnnt
reserves far more address space than it uses -- about 440 MB of mostly untouched allocator
arenas -- and a plain mlockall(MCL_CURRENT | MCL_FUTURE) populates all of it:

      resident, no locking                       8.8 MB
      resident and pinned, CURRENT|FUTURE         184 MB
      resident and pinned, +ONFAULT              10.5 MB

184 MB of unevictable memory on a 1.8 GB board, to protect a hot path needing about 9 MB.
So qnnt asks for MCL_ONFAULT as well: a page is locked the first time it is touched and
never faults again, which gives the same fault-free steady state for the memory actually
in use. System-wide Mlocked confirms it -- 10.5 MB per node, released on exit. Kernels
older than 4.4 reject the flag, and the library falls back to CURRENT|FUTURE and says so.

The consequence of ONFAULT is that warm-up still faults. Let a real-time path run once
before trusting its tail.

Four things to know before using either setting.

They need privilege, and different privileges: CAP_SYS_NICE, root, or RLIMIT_RTPRIO
(ulimit -r) for the priority; CAP_IPC_LOCK, root, or RLIMIT_MEMLOCK (ulimit -l) for the
locking. On the board both were available because the nodes ran as root; the shell's
RLIMIT_MEMLOCK was 8 MB, which root's CAP_IPC_LOCK bypasses -- an unprivileged user with
that limit would be refused. Acceptance of
the setting is not the same as the kernel granting it, so the library prints a single loud
line naming the errno if a worker is refused, and keeps running at default priority. Watch
for that line: silently missing the bound you configured is the failure mode this is
designed to make impossible.

Both are Linux only. macOS delivers real-time behaviour through thread_policy_set with a
time-constraint policy rather than POSIX priorities, and Zig's standard library does not
even declare MCL for it, so both calls are refused there with a message rather than
accepted and quietly doing nothing that helps.

MCL_FUTURE covers later mappings too, so if RLIMIT_MEMLOCK is too low the failure appears
as an allocation error somewhere unrelated to this call rather than here.

Do not combine it with an unpaced publisher (period_us 0). That is a busy loop at a
priority above everything else on its core, held back only by the kernel's RT throttle
(sched_rt_runtime_us, 950 ms of each second by default). The library warns if asked to do
both.


B.8  the whole benchmark re-run with the full real-time configuration
--------------------------------------------------------------------

B.7 showed the two settings fixing the contended 1 kHz round trip. This is every other
measurement in target B repeated with both of them on (QNNT_RT_PRIORITY=40,
QNNT_LOCK_MEMORY=1), to see where they help, where they do nothing, and where they cost.
The summary is that they are a latency configuration and behave like one: the tail improves
by up to 3x, the medians barely move, throughput is unchanged, and one combination is
actively worse.

loopback throughput, unpaced publisher:

  payload   default            FIFO 40 + mlockall     change
  64 B      253,500 f/s        267,800 f/s            +5.7%
            23.1 MB/s          24.4 MB/s
  1 KiB     158,900 f/s        157,300 f/s            -1.0%
            167.4 MB/s         165.5 MB/s
  64 KiB    3,523 f/s          3,545 f/s              +0.6%
            231.0 MB/s         232.4 MB/s

  decode 419-435 ns/frame either way; gaps 0 and badpay 0 throughout

Throughput is the same within noise, which is the expected and desired result -- nothing
here should have made the transport faster, and nothing did.

But look at the 64 B latency in that run: max went from 3.4 ms at default priority to
40.7-42.1 ms with the real-time configuration. That is not a regression in qnnt, it is the
kernel's real-time throttle. An unpaced publisher is a busy loop; at SCHED_FIFO it is a
busy loop the scheduler cannot preempt, so sched_rt_runtime_us suspends it for 50 ms of
every second, and a ~40 ms stall is exactly what that looks like from the subscriber. The
library warns when asked for both, and this is the number behind the warning.

The same thing costs throughput once the transport is the bottleneck rather than the link:

  wired board -> mac, board on FIFO 40 + mlockall (link ceiling 117.6 MB/s)

  payload   default            with the config        change
  64 B      270,000 f/s        233,900-243,800 f/s    -10 to -13%
            24.9 MB/s          21.5-22.4 MB/s         max latency 52.4 ms
  1 KiB     117.67 MB/s        117.67 MB/s            line rate, identical
  64 KiB    117.67 MB/s        117.67 MB/s            line rate, identical

So: do not put a real-time priority on an unpaced, throughput-oriented publisher. At 1 KiB
and above it makes no difference because the link is the limit; at 64 B it loses 10% and
adds 50 ms stalls. Real-time priority is for paced, latency-sensitive work.

on-board round trip, all four cells, paced so no throttle is involved:

                        default             FIFO 40 + mlockall
  20 Hz, idle           p50 832 us          p50 448-512 us
                        p99 896 us          p99 512-832 us
                        max 852-888 us      max 541-1,122 us
  20 Hz, 4 cores busy   (not measured)      p50 128 us
                                            p99 192 us
                                            max 151-198 us
  1 kHz, idle           p50 448 us          p50 448 us
                        p99 768 us          p99 448-768 us
                        max 785-1,077 us    max 768-1,071 us
  1 kHz, 4 cores busy   p50 128 us          p50 128 us
                        p99 3,648-5,376 us  p99 128 us
                        max 6,312-47,132 us max 158-212 us

Idle, the configuration changes little -- there is nothing to preempt and little to fault.
Contended, it is the difference between a 5 ms p99 and a 128 us one. And the contended cells
are faster than the idle ones at every percentile, for the reason given in B.3: busy cores
do not have to come out of an idle state.

across the wire, with only the board configured
-----------------------------------------------

The mac cannot take a real-time priority (macOS, refused), so this is the realistic
deployment shape: the embedded target is configured, the workstation talking to it is not.
node-6 on the mac, node-5 on the board, 1 KiB at 20 Hz over gigabit:

                                  p50           p90           p99           max
  board idle, board RT            2,240-2,304   2,368-2,432   2,496         2,470-2,533
  board 4 cores busy, board RT    1,600-1,664   1,728-1,792   1,856-1,920   1,865-1,925
  board 4 cores busy, default     1,600-1,664   1,728-1,792   3,968-5,248   5,248-5,551

Read the last two rows together: identical medians and p90s, and a p99 that differs by
2.7x with a worst case 2.9x apart. Configuring only the far end of the link still cuts the
tail of a round trip that spends most of its time in the network and on an unconfigured
mac. The tail was the board's scheduling, and now it is not.

Also worth noting that the busy board answers *faster* at the median than the idle one
(1.6 ms against 2.24 ms) even across the network -- the same hot-path effect, visible end
to end.

what to actually set
--------------------

  * a paced, latency-sensitive publisher or subscriber on a loaded machine: both settings.
    That is the case they exist for, and it is worth up to 40x at p99.
  * an unpaced or throughput-oriented publisher: neither. Give it a period if it needs a
    priority, or leave it at default and let it run flat out.
  * an idle machine: it makes little difference; set them anyway if the machine will not
    always be idle, since the cost when nothing is contending is not measurable here.
  * memory locking without a real-time priority is close to pointless -- the tail it removes
    is small compared with the one scheduling leaves behind. Priority first, then locking.


C.  reproducing any of it
-------------------------

Both hosts, same commit, ReleaseFast:

    zig build -Doptimize=ReleaseFast

For a target with no toolchain of its own, cross-compile for its runtime and copy the
binaries over -- this is how target B was measured:

    zig build -Doptimize=ReleaseFast -Dtarget=aarch64-linux-gnu.2.39 -Dcpu=cortex_a53

Check the target's loader and libc first (ls /lib/ld-*, ldd --version); a mismatched glibc
version fails at exec, and a static build silently ignores every QNNT_* variable.

Link ceiling and clock offset (the helper lives in the scratch dir, not the repo -- it is
30 lines of python doing a byte count and an NTP-style offset probe):

    python3 netprobe.py serve-tput 5302 20          # on the receiver
    python3 netprobe.py send-tput  <host> 5302 20   # on the sender
    python3 netprobe.py serve-clock 5301 60         # on one host
    python3 netprobe.py probe-clock <host> 5301 200 # on the other

Throughput, publisher on host A and subscriber on host B:

    # host A
    QNNT_CLUSTER_KEY=bench QNNT_REGISTRY_PORT=2222 QNNT_FEDERATION_PORT=2223 \
      ./zig-out/bin/qnnt-node-3 0 1024          # period_us=0 (unpaced), 1024 B payload

    # host B
    QNNT_CLUSTER_KEY=bench QNNT_REGISTRY_PORT=2222 QNNT_FEDERATION_PORT=2223 \
      QNNT_PEERS=<host A>:2223 ./zig-out/bin/qnnt-node-4 5000

Round trip, prober on A and echo on B:

    # host B
    QNNT_CLUSTER_KEY=bench QNNT_REGISTRY_PORT=2222 QNNT_FEDERATION_PORT=2223 \
      ./zig-out/bin/qnnt-node-5

    # host A
    QNNT_CLUSTER_KEY=bench QNNT_REGISTRY_PORT=2222 QNNT_FEDERATION_PORT=2223 \
      QNNT_PEERS=<host B>:2223 ./zig-out/bin/qnnt-node-6 50000 1024 5000

Neither host needs to know its own address: the subscriber learns the publisher's endpoint
through federation, and the address it records is the one its own connection arrived on.

Two things to know when reading the output. node-3's frames/s counts source-callback
invocations, not deliveries, so an unpaced publisher with no subscriber attached spins at
millions per second and its rate drops to the network rate once one connects. And node-4's
latency columns are only valid on one host, for the reason in section 2 -- across hosts,
read node-6 instead.
